把风险分级Agent写成**可执行的决策表**。
设计原则：
**规则先行、取最高等级、A级与CCP强制人工确认、LLM只在规则未命中或冲突时给建议且不能单独定A级**。
每条规则带编号、条件、输出等级、是否人工确认、理由模板，方便开发直接翻译成代码，也方便质量部逐条评审。

---

## 一、等级定义（先统一语义，避免规则歧义）

| 等级 | 定义 | 响应要求 |
|---|---|---|
| **A** | 已发生或极可能发生的食品安全危害，或影响整批/多批次，或CCP失控 | 立即围堵，30分钟跨部门响应，人工现场复核，24h临时遏制/72h RCA草案 |
| **B** | 过程失控或系统性偏差，尚未确认产品受影响，但有扩散风险 | 2小时响应，局部隔离/加严，3个工作日整改 |
| **C** | 孤立、局部、可立即纠正的偏差，无产品安全直接影响 | 24小时响应，7个工作日整改，记录并观察趋势 |

---

## 二、决策表：规则按优先级从高到低匹配

**匹配逻辑：所有规则并行评估，取命中规则中的最高等级；同等级多条命中时全部记录理由。**

### A级规则（食品安全/CCP/批量风险）

| 规则ID | 条件（可观测） | 等级 | 人工确认 | 理由模板 |
|---|---|---|---|---|
| A01 | 条款 `is_ccp=True` 且监控读数超出关键限值（CL） | A | **强制** | “{clause_id}为CCP，监控值{value}超出关键限值{CL}，已发生关键限值偏离。” |
| A02 | 涉及过敏原：未申报过敏原、交叉接触、标签过敏原缺失/错误 | A | **强制** | “问题涉及过敏原{hazard}，存在未申报或交叉污染风险，影响消费者安全。” |
| A03 | 致病菌指示阳性（环境/产品/接触面），或产品检出致病菌 | A | **强制** | “检出{pathogen}，产品/环境存在致病菌污染，需立即隔离并评估。” |
| A04 | 异物进入产品风险：金属/玻璃/硬塑料破损且可能进入产品流 | A | **强制** | “{foreign_object}破损，碎片可能进入产品流，构成物理危害。” |
| A05 | 冷链断链：冰鲜产品中心温度/环境温度超出可接受范围且已接触产品 | A | **强制** | “温度{temp}超出允许范围{range}，冷链断链，产品腐败/微生物风险显著上升。” |
| A06 | 清洁消毒失效且已接触产品（CIP异常、消毒浓度/时间不足、接触面残留） | A | **强制** | “{cleaning_step}失效，接触面可能残留{residue}，存在生物/化学污染风险。” |
| A07 | 批量性/系统性：同区域同问题≥3例，或跨≥2批次，或整批受影响 | A | **强制** | “同类问题在{scope}出现{n}例/涉及{m}批次，属系统性偏差，影响范围超出单件。” |
| A08 | 已售/已发货产品发现上述A类问题（追溯召回场景） | A | **强制** | “问题涉及已放行批次{batch}，需启动追溯与召回评估。” |

### B级规则（过程失控/扩散风险）

| 规则ID | 条件 | 等级 | 人工确认 | 理由模板 |
|---|---|---|---|---|
| B01 | 记录缺失/不完整，但可通过复检、追溯或补证确认产品状态 | B | 可抽确认 | “{record}缺失，暂无法确认过程受控，需补证并加严抽检。” |
| B02 | 设备参数漂移但未超出CL，或预防性维护逾期 | B | 否 | “{equipment}参数偏离设定值但未超CL/维护逾期，存在失控趋势。” |
| B03 | 一般卫生偏差：地面积水、排水口不洁、台面残留、垃圾桶未盖 | B | 否 | “{area}存在{issue}，违反SSOP卫生要求，可能滋生微生物。” |
| B04 | 人员卫生/着装不规范：未戴发网、手套破损、未按SOP洗手 | B | 否 | “{person}未遵守{hygiene_rule}，存在人为污染风险。” |
| B05 | 标识/批次记录错误但可追溯隔离，未影响放行 | B | 否 | “{label_error}导致标识不清，但批次可隔离追溯，未流入下道。” |
| B06 | 虫害设施异常（捕鼠灯/粘鼠板/风幕）但未发现虫害活动 | B | 否 | “{pest_device}异常，防控屏障失效，需修复并加严监测。” |
| B07 | 同问题30天内第2次出现（未达A07批量阈值） | B | 否 | “{issue}在30天内第2次出现，呈复发趋势，需根因分析。” |
| B08 | 供应商到货轻微偏差：包装变形、标签轻微不符，未影响产品安全 | B | 否 | “{supplier_issue}，属供应商到货偏差，需反馈并加严验收。” |

### C级规则（孤立/可立即纠正）

| 规则ID | 条件 | 等级 | 人工确认 | 理由模板 |
|---|---|---|---|---|
| C01 | 单件包装轻微变形/污渍，可立即更换，未接触产品 | C | 否 | “{packaging_issue}为孤立单件问题，可立即纠正，无产品安全影响。” |
| C02 | 工具/容器摆放不规范，未接触产品/接触面 | C | 否 | “{tool_issue}属现场定置问题，可立即整改。” |
| C03 | 记录填写笔误，可当场更正且不影响追溯 | C | 否 | “{record_typo}为笔误，可当场更正，追溯链完整。” |
| C04 | 照明/门窗/地面轻微缺陷，未影响卫生与产品 | C | 否 | “{facility_issue}为设施轻微缺陷，未构成卫生危害。” |

## 三、规则冲突与边界处理

| 情况 | 处理逻辑 |
|---|---|
| 多条规则命中不同等级 | **取最高等级**；所有命中规则及理由写入问题单 |
| 命中A级但人工确认后降级 | 必须填写降级理由和依据条款，留痕；降级后仍保留原A级规则记录供复盘 |
| 规则全部未命中 | 进入 **LLM建议分支**：LLM基于现象描述+条款原文给出建议等级+理由+引用条款；**LLM不得单独定A级**，若LLM建议A则强制转人工确认 |
| 规则命中但条件证据不足（如温度值缺失） | 按“证据不足”处理：默认不低于B，标记“待补证”，补证后重新评估 |
| 条款映射为 `no_reliable_match` | 分级Agent不自动定级，转人工选条款后再分级 |
| 同一问题既像B又像C | 默认取B（宁可过度升级，不可漏判），人工可降级并留痕 |

## 四、可执行伪代码

```python
def grade_issue(issue, clause, context):
    hits = []

    # 1) 并行评估所有规则
    for rule in RULES:                       # RULES含A01-A08, B01-B08, C01-C04
        if rule.matches(issue, clause, context):
            hits.append({
                "rule_id": rule.id,
                "level": rule.level,
                "reason": rule.render_reason(issue, clause, context),
                "need_human": rule.need_human
            })

    # 2) 无规则命中 → LLM建议分支
    if not hits:
        suggestion = llm_suggest_level(issue, clause)   # 输出 level/reason/clause_ref
        if suggestion.level == "A":
            return {
                "level": "A",
                "source": "llm_suggestion",
                "need_human": True,          # LLM不能单独定A
                "hits": [],
                "llm_reason": suggestion.reason
            }
        return {
            "level": suggestion.level,
            "source": "llm_suggestion",
            "need_human": suggestion.confidence < 0.7,
            "hits": [],
            "llm_reason": suggestion.reason
        }

    # 3) 取最高等级
    level_rank = {"A": 3, "B": 2, "C": 1}
    final_level = max(hits, key=lambda h: level_rank[h.level]).level

    # 4) 人工确认条件
    need_human = (
        final_level == "A"
        or any(h.need_human for h in hits)
        or clause.is_ccp
        or has_conflicting_levels(hits)      # 同时命中A/B或B/C
        or issue.evidence_incomplete
    )

    return {
        "level": final_level,
        "source": "rule",
        "need_human": need_human,
        "hits": hits,                        # 全部命中规则+理由
        "top_rule": max(hits, key=lambda h: level_rank[h.level]).rule_id
    }
```

## 五、人工确认界面要展示什么

分级确认页必须同时展示，避免确认人“只看等级不看依据”：

1. **最终等级 + 命中的全部规则ID和理由**（不只展示最高那条）。
2. **条款原文片段 + 来源文件/版本**（来自映射Agent）。
3. 若走了LLM建议分支：**LLM建议等级、理由、引用条款、置信度**，并明确标注“模型建议，需人工判断”。
4. **证据不足提示**：哪些字段缺失导致无法命中规则。
5. **调整入口**：可升级/降级，但降级必须填理由；A级降级需质量授权人。
6. **历史同类问题**：该区域/条款近30天同类问题次数，辅助判断是否系统性。

## 六、离线评测与调参

用历史巡检记录构造评测集（建议≥100条，A/B/C各覆盖）：

```python
for issue in eval_set:
    pred = grade_issue(issue, issue.clause, issue.context)
    record(pred.level, issue.gold_level, pred.hits, pred.need_human)

metrics = {
    "A_recall": ...,          # A级漏判率，最重要，目标接近100%
    "A_precision": ...,       # A级误升级率
    "overall_agreement": ..., # 与专家分级一致率
    "human_confirm_rate": ...,# 人工确认负担
    "llm_branch_rate": ...    # 规则未命中比例，过高说明规则表覆盖不足
}
```

调参原则：
- **A级召回优先**：宁可多升级人工确认，不可漏判A。
- `llm_branch_rate` 高 → 补规则或补条款库，不是放宽LLM权限。
- `human_confirm_rate` 过高 → 检查是否A级规则过宽或证据字段缺失导致误触发。

## 七、规则表维护机制

- 每条规则有**版本号、生效日期、owner（质量部）**，修改留痕。
- 新增规则来源：LLM分支中人工最终定级与建议不一致的样本、A级漏判复盘、法规/HACCP变更。
- 规则表**每季度评审一次**，重点看：A级漏判、频繁被人工降级的规则、从未命中的规则。
- 规则与HACCP条款的关联关系显式维护，HACCP计划修订时自动提示相关规则需复核。
