## 零、先记住这四句话（被问住时的兜底）

1. **LLM 只做抽取、检索、语义核验；分级和放行是规则的事。**

## 一、30 秒电梯讲稿

> 这是一个食品工厂巡检整改的多Agent闭环系统。
>
> 它解决三个很具体的问题：巡检员说的"地面积水"跟 HACCP 条款对不上，要翻半天表；风险分级靠人拍脑袋，容易错；更麻烦的是整改时口头答应、表上写改了其实没改。
>
> 我把它拆成三个专业Agent：条款映射做检索和置信度分流，风险分级用20条规则决策表，证据验证做五道闸门，重点是元数据防旧图、哈希和相似度防复用、VLM判断照片是不是真对应整改项。
>
> 架构上我没做成多个Agent自由聊天协商——食品安全场景里Agent互相说服的代价是整批货放行。用的是LangGraph状态机做骨架，Agent只输出结构化结果写共享状态，什么时候调哪个、低置信度转人工、A级强制确认、证据打回回到哪一步，都是编排器的条件边和硬闸门决定的，Agent无权绕过。
>
> 核心不是让AI替人品控，而是让查表、分级、验证据这三件耗人又容易出错的事被系统接住，决策权还在人手里。

## 二、2 分钟完整讲稿（主用）

> **背景**（15秒）
>
> 食品工厂巡检有三个反复出现的痛点。第一个，巡检记录是口语化的，跟 HACCP/SSOP 条款对不上，质量员得对着表查半天。第二个，风险分级是人工判断，A级漏判的代价是整批货放行。第三个最隐蔽——整改时口头答应、表上写改了其实没改，有的甚至拿上次整改的照片重复交。
>
> **我的设计原则**（20秒）
>
> 贯穿全项目一句话：**LLM负责抽取、检索和语义核验，规则负责分级和闸门，人工保留A级确认和现场复核权**。这不是姿态，是硬编码在代码里的。
>
> **三个Agent**（50秒）
>
> 条款映射，难点是巡检口语和条款书面语之间的语义鸿沟。所以不是"拿一句话去向量库搜一下"，而是：先抽查询要素（现象、区域、工序、危害类型），再按区域工序做元数据硬过滤缩小候选池，然后向量和BM25双路召回、RRF融合、rerank重排。置信度不是单看向量分数，而是rerank分数、双路一致性、元数据匹配三路信号合成——因为单分数没法区分"检索偏了"和"条款库缺项"这两种完全不同的失败。然后分三档：高分预填、中分必须人工选、低分显式弃答不预填。**低置信度不硬猜是硬约束**，因为预填错条款比不预填更糟，它会一路污染后面的分级。
>
> 风险分级，用20条可执行规则做成决策表，A01到C04。设计上两个要点：所有规则并行评估取最高等级，串行的话会在第一个规则处短路，结果依赖规则表顺序，很脆弱；同等级多条命中时理由全部记录，不只展示最高那条。LLM只在规则全部未命中时给建议，而且**LLM不能单独定A级**——建议A就强制转人工。另外证据不足时默认不低于B，宁可过度升级不可漏判。
>
> 证据验证，五道闸门顺序执行：清单完整性、元数据防旧图、哈希加感知哈希防复用、VLM语义核验、交叉校验。任一道打回立即终止。这里有个刻意的取舍：**VLM输出三态，只有"明确不符且置信度≥0.8"才自动打回，存疑一律转人工**。因为VLM判定方差大，光照角度遮挡都影响结果，如果把"不确定"当"不合格"，现场就会开始想办法绕过系统。
>
> **架构**（25秒）
>
> 编排用LangGraph状态机，11个状态23条转换边，每条转换边都在显式的合法转换表里，非法转换直接抛错。Agent之间不直接对话，只通过Pydantic约束后的共享状态读写。硬闸门写在编排器不在Agent里——Agent自己说"我判定完了"没用，编排器该拦还是拦。三个硬闸门：低置信度条款映射不得自动定级；A级和CCP问题不得仅凭照片自动关闭；打回不重置倒计时。第三条是防拖延的关键：打回只增加无效整改次数，截止时间不动，否则整改人最优策略就是先随便交点什么被打回，倒计时一重置再拖几天。
>
> **成果**（15秒）
>
> 31个单元测试全绿，覆盖全部硬闸门；三条评测线跑出了基线：条款映射Top-3命中率96%、错误预填率3.7%；分级A级召回100%；证据验证在120条构造样本上误杀率0%。阈值不是拍脑袋定的，是用网格搜索在16组阈值里选的——原则是错误预填率优先压低，再在这个前提下尽量提高预填率。

## 三、5 分钟深挖版（技术面用）

在 2 分钟讲稿基础上，按追问方向展开：

### 3.1 条款映射：RAG 流水线

```
巡检口语描述
  → ① 查询要素抽取（LLM + schema约束，失败字段留空不阻断）
  → ② 元数据硬过滤（zone→process→hazard 逐层放宽，记录放宽层级）
  → ③ 双路召回（向量 + BM25，各 k=10）
  → ④ RRF 融合（k=60，只看排名不看分数）
  → ⑤ rerank（cross-encoder / LLM listwise，取 Top-5）
  → ⑥ 多信号置信度合成
  → ⑦ 三档分流：预填 / 人工选Top-3 / 显式弃答
```

**为什么用 RRF 而不是加权求和**：向量检索分数是 0~1 余弦，BM25 分数能到十几，量纲完全不同。加权求和必须先归一化，而归一化方式会显著影响结果。RRF 用 `1/(k+rank)` 只看排名，对异构分数最鲁棒。

**为什么先硬过滤再全库召回**：全库盲召回时，"温度记录缺失"会同时召回 HACCP 的 CCP-01 和 GMP 的设备校准条款。过滤先砍掉不适用区域/工序的，让 rerank 在更干净的候选集上工作。候选少于 20 条才逐层放宽，并把放宽了哪一层记进 `relaxed_filter_layers`，可观测。

**为什么置信度要三路信号**：

| 信号 | 作用 |
|---|---|
| rerank 归一化分数 | 基准分 |
| 双路一致性 +0.10 | 向量和 BM25 都排 P70 前 → 语义和关键词同时命中 |
| 区域/工序/危害类型各 +0.05 | 元数据硬过滤没失效 |
| RRF 先验 | 兜底，防分数抖动 |

单看分数无法区分"检索偏了导致高分错配"（最危险，会误导分级）和"条款库缺项导致全都不高"（该转人工补库）。

**CCP 特殊处理**：命中 `is_ccp=True` 的条款**不额外加分，但强制人工确认**。CCP 误分级的代价远高于多一次人工确认的成本。

**版本处理**：知识库按条款编号分块，一个条款一个 chunk，保留版本号、生效日期、原文、适用区域/工序/是否CCP/危害类型。检索时只取 `effective_date <= 今天` 的最新版本，过期条款不进候选。条款库导入时元数据由质量部人工校验——`is_ccp` 抽错了，硬过滤就全错。

**人工回流**：人工最终选定的条款连同候选列表和原始 Top-1 一起存进样本库，统计 Top-1 准确率、Top-3 命中率、人工改选率、无可靠匹配率。**只入库做离线评估，不在线自动训练模型**——few-shot、阈值调整、rerank 微调都基于样本库离线进行。

### 3.2 风险分级：规则决策表

20 条规则，A01–A08 / B01–B08 / C01–C04，每条带 `rule_id`、可观测条件、等级、是否需人工确认、理由模板。质量部能逐条评审。

**并行评估取最高等级**——串行会在第一个命中处短路，结果依赖规则表顺序。

**LLM 建议分支**：规则全未命中时才走。LLM 建议 A → 强制人工；建议 B/C 但置信度 <0.7 → 人工确认。

**证据不足处理**：比如描述里提"温度异常"但没给具体数值，规则 A01 的关键限值条件无法验证 → 标记"待补证"，且**默认不低于 B**。宁可过度升级，不可漏判。

**人工降级留痕**：A级降级必须填降级理由（代码层 `ValueError` 强制），原等级保留在 `original_level` 供复盘，审计日志记改前改后。

### 3.3 证据验证：五道闸门

| # | 校验 | 规则 | 关键拦截 | 成本 |
|---|---|---|---|---|
| 1 | 清单完整性 | E101–E104 | 必交缺项 → 打回 | 极低 |
| 2 | 元数据 | E201–E208 | EXIF 早于派单 → 疑似旧图打回 | 极低 |
| 3 | 历史复用 | E301–E305 | sha256 一致 / pHash ≥0.95 → 打回 | 低 |
| 4 | 语义核验 | E401–E406 | VLM 明确不符 → 打回；文档字段矛盾 → 打回 | 高 |
| 5 | 交叉校验 | E501–E504 | 与 MES/设备日志矛盾 → 存疑；复检不合格 → 打回 | 中 |

**排序逻辑**：先便宜后昂贵。前 3 道确定性最强、成本最低，能拦住"表上写改了其实没改"的大多数情况。建议先上线 1–3 道，用真实历史照片库把相似度阈值调稳，再开第 4 道的自动打回权限。

**证据类型不可自选**：必交清单由**问题类型 + 等级**决定（`REQUIRED_EVIDENCE` 表）。例如"地面积水"要求整改后照片+清洁记录；"温度记录缺失"要求温度仪导出文件+校准状态截图+补录说明。整改人不能删必交项，缺项在第 1 道直接打回。A级额外追加临时遏制证明。

**pHash 三档阈值**：

| 相似度 | 判定 | 理由 |
|---|---|---|
| ≥ 0.95 | 打回 | 几乎确定同一张图 |
| 0.85–0.95 | **存疑** | 可能是同一场景重拍（同一台设备连续整改） |
| < 0.85 | 通过 | 真实复用几乎不会低于此值 |

中间档必须存疑——同一处积水整改前后背景天然相似，单阈值必然误杀真整改。

**打回后果**：
- 倒计时**不重置**，只 `invalid_fix_count += 1`
- 连续打回 2 次 → 升级一级响应；3 次 → 通知厂长/质量总监
- A级任何一次打回 → 强制质量经理知悉
- 无效整改次数进责任部门月度统计

**分级分流**：

| 分流 | 后续 | 处理人 |
|---|---|---|
| reject | 无效整改+1，倒计时继续 | 系统 |
| human_onsite_review | 现场确认签字后才进复查 | 质量授权人 |
| human_review | 远程复核证据+关联记录 | 质量工程师 |
| auto_pass | 进复查抽验 | 系统 |

**A级/CCP 无论自动结果如何都转现场复核**——硬规则，且不计入自动通过率统计。

### 3.4 编排与工程化

**状态机**：草稿→待映射→待分级确认→待整改→待验证→待复查→已关闭，旁路打回重开/存疑复核/升级CAPA/延期审批。11 状态 23 条边，`ALLOWED_TRANSITIONS` 显式声明，非法转换抛 `TransitionError` 不静默通过。

**审计**：每次转换记操作人/Agent、时间、输入输出摘要（sha256 摘要）、置信度、人工修改前后值、引用来源、Agent版本、问题单版本号。审计表**只暴露 append 接口，没有 update/delete**。

**幂等**：状态转换带幂等键，重复提交返回既有记录并留痕。配合版本号防止重复派单。

**降级**：LLM 不可用或输出不合规 → 降级规则分支 + 人工复核，**绝不自动放行**。确定性规则分支直接短路不调 LLM，控制成本和延迟。

**复查抽验**：A级 100% / B级 40% / C级 15%，**不预先通知现场**。复查不通过等同无效整改。

**CAPA 联动**：同区域+工序+条款 30 天内复发 → 自动升级 CAPA 并触发 HACCP 计划/SSOP 评审提醒。

## 五、追问预案（按被问概率排序）

### Q1 "这个项目上线了吗？"

> 没有，这是**可运行的工程原型**。我把完整链路、三个Agent、状态机、硬闸门、五道校验、评测和API全部实现并跑通了，但没在真实工厂部署。
>
> 没做的部分我明确说一下：条款库是我内置的15条示例条款，不是企业真实的HACCP计划；向量检索用的是可复现的hashing投影不是真实embedding模型，BM25和rerank都是自实现的轻量版本；VLM是mock的启发式实现，真实视觉模型要在真实照片库上重新测误判率；存储用SQLite，生产该上PostgreSQL。
>
> 但**闸门逻辑、状态机约束、规则表结构、评测框架**这些是按生产标准写的，替换组件不需要动这部分。

**为什么要主动说**：面试官问这题是必然的。说"原型"但展示出对生产差距的清醒认知，比吹"已上线"然后被追问细节当场崩掉强得多。

### Q2 "你这个 100% 准确率是不是太夸张了？"

> 这题问得好，那个数字确实不能这么理解。
>
> 分级一致率 100% 是因为**评测集只有22条，而且规则表和样本是我同源写的**——它验证的是规则逻辑和闸门行为是否正确，不是泛化性能。真实场景下质量专家会给出不同的分级，尤其边界case。
>
> 我把它定位成**基线和回归测试**：改了规则表之后，跑一遍看有没有退化。真正要拿去支撑上线决策，得让质量部独立标注100到200条历史巡检问题，而且标注的人不能是我。
>
> 我更愿意相信另外两个数字：错误预填率3.7%——这个是27条独立标注样本上算的，而且它是**约束性指标**（预填错条款比不预填更糟）；误杀率0%——120条构造样本，四类各30条，逻辑上应该是对的，因为构造方式明确，但**样本是构造的不是真实的**，真实场景的误杀率一定更高。

### Q3 "为什么不用微调一个模型直接做分类？"

> 因为**错误代价不对称**。分类错了可以直接拿模型输出，但"定级"这个动作的下游影响太大——A/B/C决定时限、证据清单、是否强制现场复核、复查比例。把它交给一个概率模型，出了问题没法解释、也没法追责。
>
> 更实际的问题是**法规和HACCP计划会变**。规则表改了是改几行配置，模型微调了要重新训、重新评、重新走上线流程。规则表还有个好处是**质量部能逐条评审**——每条规则带条件、等级、理由模板，能看懂能驳回。
>
> 所以我的取舍是：**规则表做确定性判定，LLM 只在规则没覆盖到的地方给建议**。而且LLM建议A级也强制转人工，模型不得单独定A。

### Q4 "多条规则都命中怎么办？为什么这么设计？"

> 取最高等级，理由全部记录。
>
> 关键是**并行评估**。如果串行，第一个命中的规则就返回了，结果完全依赖规则表顺序——把A02（过敏原）和B03（卫生偏差）的顺序调一下，"标签过敏原缺失+地面积水"就从A级变成B级了。这种脆弱性在食品安全场景不可接受。
>
> 并行评估让结果与规则顺序无关。同等级多条命中时理由全记，因为质量员确认时需要知道"为什么是B级"，不能只看最高那条就签字。

### Q5 "置信度怎么算的？为什么不直接用向量相似度？"

> 三路信号合成：rerank归一化分数做基准，双路一致性加0.10，区域/工序/危害类型匹配各加0.05。
>
> 不用单一向量分数的原因是**它区分不了两种失败**。一种是"检索偏了"——排第一的那个条款其实不对，但分数很高，这会给出高置信度的错误预填，是最危险的情况，因为预填错的条款会一路流到分级去污染判断。另一种是"条款库缺项"——所有条款分数都不高，这时候应该转人工去补库。前者要拦，后者要放行，单分数做不到区分。
>
> 另外双路一致性是个强信号：向量和BM25都排前面，说明语义和关键词同时命中了。

### Q6 "打回不重置倒计时，为什么这么设计？"

> 这是防拖延的关键。前面三条硬规则（证据类型不可自选、证据必须新鲜、历史复用检测）都是**检测假证据**，第四条是**惩罚拖延**。
>
> 如果打回后倒计时重置，整改人的最优策略就变成了：先随便交点什么被打回，倒计时一重置，再拖几天。对B级3个工作日的问题，这个循环能让它无限期悬置。
>
> 所以打回只增加无效整改次数，截止时间严格不动。然后连续打回2次升级一级响应，3次通知厂长，无效整改次数进部门月度统计——**让"表上假改"有实际成本**。打回也不能作为延期理由，延期要质量授权人批准并留痕。

### Q7 "证据验证误杀了真整改怎么办？"

> 这是我最在意的一个设计取舍。误杀真整改会**摧毁现场对系统的信任**，一旦大家觉得"这系统老冤枉我"，就会开始想办法绕过它，那整套防假改就白做了。所以我的阈值策略是：
>
> 1. **VLM只对明确不符自动打回**。VLM输出三态，`mismatch`且置信度≥0.8才打回，`uncertain`一律转人工。我不把"不确定"当"不合格"——光照、角度、遮挡都会影响VLM判定，把不确定当不合格，现场立刻会开始糊弄。
> 2. **pHash相似度分三档**，0.85到0.95是"存疑"不是"通过"。同一台设备、同一处积水，整改前后拍的照片背景天然相似，如果用单阈值必然误杀。
> 3. **无EXIF判存疑不判打回**。水印相机本来就没EXIF，不能因此认定旧图。
> 4. **上线策略**：建议先只开校验1到3道——这三道确定性最强、成本最低，能拦住大部分"表上写改了其实没改"。第4道的自动打回权限等真实照片库调稳阈值后再开。
>
> 评测上误杀率是硬指标，目标是控制在5%以内。

### Q8 "状态机怎么保证不出现非法流转？"

> 用显式的合法转换表 `ALLOWED_TRANSITIONS`，11个状态23条边。所有转换走一个 `_transition()` 入口，非法目标状态直接抛 `TransitionError`，不静默通过。
>
> 为什么不用"随便改state字段"：那样非法流转会静默发生，事后审计才发现，食品场景下就是追溯问题。我把它做成**测试会失败的那种约束**——有专门的反向测试验证从"待整改"直接跳"已关闭"会被拒。
>
> 审计日志是只追加的，仓储层只暴露 append 接口，没有 update 和 delete。

### Q9 "为什么用 LangGraph？自己写状态机不行吗？"

> LangGraph 的价值主要是**条件边 + checkpoint**。条件边正好对应我的硬闸门——低置信度走人工分支、A级走确认分支、证据打回走重开分支，写成边比写一堆 if 清晰。而且checkpoint支持中断和恢复，人工审核要等好几天，状态得能存住。
>
> 但我**没有把逻辑绑死在LangGraph上**。编排逻辑在 `orchestrator.py` 里是显式的状态机，LangGraph那层只是把同一套路由用条件边表达出来。LangGraph没装的时候自动回退到等效的显式流转实现，两条路径行为一致。这不是过度设计——因为**规则分支不调LLM，状态流转是系统里最该稳定的那部分**，它不该依赖一个第三方库的版本。

### Q10 "这个系统实际能省多少人力？"

> **我没有真实工厂的对照数据，不能编这个数。** 我能说的是系统层面的指标：自动流转率、人工介入率、待人工任务积压量、平均闭环时长、非法状态转换次数，这些我在 `stats` 接口里都实现了。
>
> 从设计上看，节省的是**查表和分级这两件的耗时**——巡检员不用等质量员查条款，质量员不用逐条拍脑袋分级。但人工介入点一个都没减少：A级确认、CCP现场复核、存疑复核，这些是刻意保留的，因为**这些恰恰是不该让AI替人做的决策**。
>
> 真正想验证的是另一件事：**无效整改次数下降**。这才是"表上假改"这个痛点的直接度量。但这个要等真实数据。

### Q11 "条款映射的召回效果如果不好怎么办？怎么定位？"

> 分三步定位，这是我在设计时就留的观测点：
>
> 1. **查询抽取有没有错**——记录了抽取的要素和是否成功。抽取失败时走全库双路召回并标注"要素缺失"，强制人工选。
> 2. **召回有没有召回**——记录了候选池大小、过滤放宽了哪一层、向量和BM25各自的排名和分数。硬过滤把正确条款滤掉了，是过滤层的问题；滤对了但没进Top-K，是召回层的问题。
> 3. **重排有没有排上来**——记录了rerank前后的排名变化。
>
> 人工改选的结果全部回流样本库，`top1_was_correct=False` 的样本优先人工看，判断是检索问题、条款粒度问题、还是条款库缺项。**这三种问题的修法完全不同**，所以必须能区分开。

### Q12 "如果条款库版本更新了怎么办？"

> 知识库每个条款保留版本号和生效日期。检索时只取 `effective_date <= 今天` 的最新版本，旧版本不进候选。输出时再校验一次版本，过期则降权并提示。
>
> 另外规则表和条款的关联关系是显式维护的，**HACCP计划修订时会自动提示相关规则需要复核**——因为条款改了，判定条件可能就不成立了，比如CCP的CL从4℃改成3℃，那A01规则的判据就得跟着改。这条我在规则表维护机制里写了。

### Q13 "为什么不联网搜、用现成的RAG框架？"

> 用了LangGraph和FastAPI这些现成的。但RAG这一层我是自己写的，原因有三：
>
> 1. **元数据硬过滤 + 逐层放宽 + 记录放宽层级**这个逻辑，通用RAG框架的filter接口做不到这么细，它要么过滤要么不过滤。
> 2. **RRF融合 + 多信号置信度**要和控制器的分流逻辑耦合在一起做，拆开反而更绕。
> 3. 最实际的——**离线能跑**。向量库、rerank这些用真实组件意味着要下载模型、要装重依赖。我用可复现的hashing投影做向量、BM25自实现、rerank用交叉特征，这样整套流水线在离线环境可跑可测，面试时能当场demo。接ChromaDB或者FAISS的话，只需要覆盖 `vector_search` 和 `rerank` 这两个方法，过滤、融合、置信度、闸门、状态机全都不用动。

### Q14 "你的VLM怎么判断照片符不符合整改项？"

> 结构化输出，三态：`verdict` 是 match/mismatch/uncertain，加 confidence、reason、evidence_refs。不允许自由文本，因为后续要拿verdict做路由判定，reason只给人看。
>
> 判定依据是整改要求本身——比如要求是"地面积水"，判断依据就该是"照片里地面是否干燥无积水"，这是有明确视觉判据的。我这里是mock实现，通过文件名标注模拟判定，**真实模型要接进来之后重新测误判率和存疑率**。
>
> 存疑率过高时的处理是：**先只对明确不符打回，其余转人工**，不要为了提高自动判定率去调模型，那是拿误杀换自动化率。

### Q15 "为什么用Pydantic约束？"

> 因为**Agent之间不直接对话，只通过共享状态读写**，那共享状态就是接口。接口必须有契约，否则一个Agent改了字段名，另一个Agent的输出就静默丢失或者直接崩。
>
> 契约的作用还有一层：所有Agent输出**先过Schema校验才允许进入状态机**。LLM输出不合规的时候，校验会失败，然后降级到规则分支+人工复核，而不是让一个格式错误的结构污染下游。
>
> 而且Schema本身就是文档——`GradeResult` 里 `hits` 存的是全部命中规则和理由，`original_level` 存降级前的等级，`evidence_gaps` 存哪些字段缺失导致判不了，审计和前端展示都直接用它。

### Q16 "怎么保证幂等和重复提交？"

> 状态转换带幂等键，仓储层有 `claim_idempotency_key`，用唯一索引占位。重复提交时返回既有记录并在审计里留一条 `idempotent_replay` 记录——**重放本身也是审计事件**，这样能看出前端是不是在重试。
>
> 每个问题单还有版本号，每次状态转换递增。这个版本号和审计记录的 `version_no` 一起用，理论上可以做乐观并发控制防止两个操作员同时改一张单。

| 问什么 | 答什么 |
|---|---|
| 知识库怎么分块 | **按条款编号切，不按token切**。一个条款一个chunk，长条款额外生成摘要块但召回时原文块优先 |

| 双路召回各取多少 | k=10，rerank后取Top-5，置信度分档用Top-3给人选 |
| 元数据过滤放宽顺序 | zone → process → hazard，逐层放宽，记录放宽层级 |
| 分级三档定义 | A=已发生/极可能危害、影响整批、或CCP失控；B=过程失控有扩散风险；C=孤立可立即纠正 |

| 升级路径 | A：班组长→车间主任→厂长/质量总监；B：班组长→车间主任→质量经理；C：班组长→车间主任 |

| 幂等键 | `issue_id:state:version` + 仓储唯一索引占位 |
| 数据库 | SQLite（可换PostgreSQL，仓储层接口已隔离） |
| 代码规模 | 5380行 Python（含测试和脚本），31个单元测试 |

## 七、演示脚本（如果能现场跑）

```bash
cd 桌面/食品项目
python scripts/demo_end_to_end.py
```

**四个场景对应四个卖点，讲解时按顺序说：**

1. **场景1 正常闭环**（B级卫生问题）
   → 自动预填条款 → 自动分级 → 自动派单 → 证据通过 → 复查关闭
   *话术：这条走完全自动，说明系统不是"什么都让人审"*

2. **场景2 A级过敏原**
   → 强制人工确认分级 → 证据全部校验通过**仍然**转现场复核 → 签字才关闭
   *话术：A级证据明明五道校验全绿，系统还是不自动放行——因为决策权在人不在机器*

3. **场景3 旧图复用**
   → 五道校验在第3道 `E301` 打回 → **倒计时前后完全一致**（屏幕上打两个时间戳对比）→ 重新提交才通过
   *话术：这是核心卖点。倒计时不重置，拖不了*

4. **场景4 无可靠匹配**
   → 显式弃答 → 尝试自动分级被**当场拦截**（抛异常）→ 人工选条款后才能继续
   *话术：低置信度不硬猜，而且这个约束是代码强制，不是靠提示词自觉*

app/agents/evidence_verify_agent.py → 五个 check_* 方法，规则ID和设计稿一一对应

tests/test_agents.py            → 反向测试：验证系统"不做什么"

## 九、一页速记卡（面试前 10 分钟看这个）

**项目名**：巡检整改多Agent闭环系统（条款映射 / 风险分级 / 证据验证）

**一句话**：LLM做抽取检索核验，规则做分级闸门，人保留A级确认和现场复核权

**三个 Agent**
1. 条款映射：要素抽取→元数据硬过滤→向量+BM25→RRF→rerank→多信号置信度→三档分流
2. 风险分级：20条规则并行取最高；LLM不能单独定A；证据不足不低于B；降级留痕
3. 证据验证：五道闸门（清单/元数据/复用/语义/交叉）；打回不重置倒计时；A级强制现场

**三条硬闸门**（写进代码，不是写进文档）
1. 低置信度不得自动定级
2. A级/CCP 不得仅凭照片关闭
3. 打回不重置倒计时

**数字（务必带上限定词）**
- 条款映射 Top-3 96.3% / 错误预填 3.7%（27条独立标注样本）
- 分级 A级召回 100%（22条同源样本，逻辑验证非泛化）
- 证据验证 误杀 0%、打回精确/召回 1.0（120条构造样本）
- 31个测试全绿 / 20条规则 / 11状态23边 / 5380行

**最大卖点**：不是"AI替人品控"，是"让查表、分级、验证据这三件耗人又易错的事被系统接住，决策权还在人手里"

**最大风险**：别把原型说成上线，别把同源评测说成泛化能力
