1巡检整改多Agent闭环系统

食品工厂巡检整改 · 条款映射 / 风险分级 / 证据验证

全栈 + Agent 架构 + 产品设计独立完成5,381 行 Python 31 个单元测试16 个 API 端点

针对食品工厂巡检的三个痛点——问题与 HACCP 条款对不上、人工分级易错、整改口头答应表上假改—— 构建由三个专业 Agent 组成的整改闭环系统。架构采用 Orchestrator + 共享状态 + 条件路由 + 硬闸门 + Human-in-the-loop， Agent 之间不直接对话，只读写经 Pydantic 约束的共享状态。

改造前 巡检员手写记录 → 班组长翻 SSOP 手册查条款（20–40 分钟/条）→ 凭经验定 A/B/C → 口头交代整改 → 交张照片就签字 → 超时没人催
改造后 自动结构化录入 → RAG 召回 Top-3 条款供选 → 20 条规则判定并留痕 → 自动派单含必交证据清单 → 五道闸门验证据 → 超时按级自动上推

三条写进代码的硬闸门

1
低置信度条款映射不得自动定级——必须人工选条款，绕过时抛 TransitionError
2
A级 / CCP 问题不得仅凭照片关闭——无论自动校验结果如何，强制人工现场复核
3
打回整改不重置倒计时——只增加无效整改次数，否则整改人最优策略是"随便交点被打回，倒计时一重置再拖几天"

RAG 流水线与置信度合成

巡检口语描述 → ① 查询要素抽取（失败字段留空不阻断） → ② 元数据硬过滤（zone→process→hazard 逐层放宽） → ③ 向量 + BM25 双路召回 → ④ RRF 融合（k=60，只看排名不看分数） → ⑤ rerank 取 Top-5 → ⑥ 置信度多信号合成 → ⑦ 三档分流：预填 / 人工选Top-3 / 显式弃答

置信度由 rerank 分数 + 双路一致性 + 元数据匹配 三路信号合成， 不用单一向量分数——单分数区分不了"检索偏了导致高分错配"（最危险，会误导分级） 和"条款库缺项导致全都不高"（该转人工补库）。 命中 CCP 条款不额外加分，但强制人工确认。

面向消防执法场景的多模态系统。网关统一鉴权审计、三级级联路由、三态熔断降级、 LangGraph 状态图编排、人机协同审批流——不是单点 Demo，而是有工程约束的完整系统。

工程化能力

  • 三态熔断 closed / open / half-open，下游挂掉时降级而非整体卡死
  • 统一鉴权 内部 Token 常数时间比较防时序攻击，clearance 越界收敛
  • 提交历史 安全修复 → 测试补齐 → CI 引入 → 文档重写，按优先级排序

业务侧设计

  • 文书改动检测 Agent 自动 diff 原稿与人工改后稿，解决四个审批盲区
  • 三级字段分流 事实 / 法律 / 待补充——第三类留空标记，绝不编造条款

  • 语音交互 讯飞听写 / Whisper 离线识别 + 多引擎 TTS

RAG 调优：5 轮迭代的完整归因

起点 context_precision 0.165，但"低在哪、为什么低"完全未知。 先把评测集从 5 条扩到 47 条人工标注（三个维度分层），再动手优化。

踩到的第一个陷阱：扩充评测集后总分从 0.95 掉到 0.48，第一反应是"代码退化了"。 分层统计后发现老 7 条 recall 仍是 1.000，新加 40 条只有 0.444——是样本拉低了总分，不是代码退化。 方法论：指标变化必须先归因到"样本变化"还是"代码变化"。

最核心的技术判断： 单因素实验（局部变化）与正交实验（全局变化）数据生成机制不统一， 混在一起建模 R² 会变负。分层处理——单因素用二次拟合、正交用 GPR——才有了 0.64。 选 GPR 而非随机森林，是因为贝叶斯优化需要不确定性估计，这是对下游任务的考量。

4AI 协作方式

分层委派：翻译型交给 AI，判断型自己扛

我的协作方式不是"让 AI 写完我检查"，而是按任务性质分层： 翻译型（写模型、实现检索、补测试）交给 AI 提高速度； 判断型（该做成什么样、哪些约束不可绕过）我自己决定。

四道质量门禁（会失败，不是走过场）

  • 单元测试 105 个用例（31 + 74），重点是反向测试
  • 端到端演示 4 个真实场景，覆盖全部硬闸门
  • 离线评测 三套评测 + 阈值网格搜索，输出指标报告
  • CI GitHub Actions 推送自动跑测试与代码规范

实际踩过的坑（都是真卡住过的）

  • 状态机漏边 + 异常被静默吞掉 → 输出"全绿"但流程全卡住
  • 路径层级少算一级 → 数据落到错误目录，不报错只存错地方
  • AI 倾向"把不确定当通过" → 无 EXIF 被直接打回，会误杀真整改
  • 指标漂亮得不像话 → 22 条同源样本，只能验证逻辑不能验证泛化
关于 AI 署名：两个项目的 git 历史都保留了 Co-Authored-By 标注， 这是主动披露而非隐藏。我负责的是需求拆解、架构决策、硬约束设计和最终验证—— 比如"打回不重置倒计时"这条业务规则，是我在设计时推导出后果后要求写进代码的， AI 负责把它翻译成实现和测试。

6边界声明

把话说清楚，比说得漂亮更有用。以下是本作品集内所有系统共同的边界：

  • 未在真实生产环境部署——有 Dockerfile 与编排配置，但没在工厂/客户环境跑过
  • 默认跑 mock LLM/VLM——接口已就绪（OpenAI 兼容协议），真实模型接入后行为会有差异
  • 向量检索为自实现 hashing 投影，非 ChromaDB/FAISS——为保证离线可跑，替换只需覆盖一个方法
  • 条款库是内置 15 条示例，非企业真实 HACCP 计划
  • 评测样本量小且部分同源——分级 100% 一致率仅验证逻辑正确性，真实泛化需独立标注 100–200 条复核
  • 无真实人力节省数据——指标采集接口已实现，但没有真实数据源，不编这个数
  • 三个项目均为个人独立完成——团队协作经验不足，这是我明确知道的短板
GitHub 仓库 ×2 项目 README 架构文档 评测报告 面试材料

贯穿三个项目的一句话：不是让 AI 替人判断，而是让系统接住那些耗人又容易出错的事， 把决策权留在人手里。
