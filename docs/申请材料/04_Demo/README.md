## 一、三分钟跑通（最推荐的演示方式）

```bash
cd 食品项目
pip install -r requirements.txt

python scripts/demo_end_to_end.py
```

**预期输出**：4 个场景依次执行，每个场景打印完整的决策链路、闸门判定和审计轨迹。

### 场景与演示话术（按顺序讲，每段 30 秒）

#### 场景 1：B级卫生问题 —— 全自动闭环

> "这条从录入到关闭全程自动：条款映射预填、B级规则判定、自动派单、证据五道校验通过、复查关闭。
> 说明系统不是什么都让人审——人工介入点是刻意保留的，不是默认开的。"

**看点**：状态从"草稿"走到"已关闭"，版本号 v1→v6。

#### 场景 2：A级过敏原 —— 强制人工

> "这是 A 级。关键在最后：五道校验**全部通过**，系统仍然不自动放行，转人工现场复核。
> 因为 A 级的决策权不在机器。"

**看点**：输出里的 `route=human_onsite_review`，以及前面一排 ✓ 的校验结果。

#### 场景 3：旧图复用 —— ★ 最能证明约束生效

> "整改人把上次整改的照片又交了一次。第三道校验 E301 直接打回。
> 更重要的是看这两个时间戳——**打回前后完全一样，倒计时没有重置**。"

**看点**：终端输出这一行——
```
截止时间是否被重置：否（正确，保持不变）  2026-10-20T... → 2026-10-20T...
```

**为什么这个场景最有说服力**：它演示的不是"功能可用"，而是**"约束真的生效"**。
功能演示谁都能做，约束演示才能说明设计意图被落地了。

> 补充一句加深印象："如果打回后倒计时重置，整改人的最优策略就是先随便交点什么被打回，
> 倒计时一重置，再拖几天——对 B 级 3 个工作日的问题能让它无限期悬置。"

#### 场景 4：条款库无对应项 —— ★ 演示"闸门拦截"

> "这条巡检描述在条款库里找不到对应项。系统没有硬猜，而是显式弃答。
> 然后我故意尝试在人工选条款之前自动分级——**当场抛异常**。"

**看点**：
```
映射结果 mode=no_reliable_match
硬闸门验证 —— 尝试在未人工选条款前直接分级：
    ✓ 被拦截：条款映射为 no_reliable_match，必须先人工选条款才能分级
```

## 二、评测与测试（展示质量意识）

```bash
# 三套离线评测 + 阈值网格搜索
python scripts/run_eval.py

# 31 个单元测试
python -m pytest tests -q
```

**话术**：
> "评测跑完会输出三套指标和一个 16 组阈值网格搜索结果。
> 阈值不是拍脑袋定的——原则是错误预填率优先压低，再在这个前提下尽量提高预填率。
> 最终选定 high=0.70 / mid=0.45，预填率从 37% 提到 52%，错误预填率不变。"

**如果被问"100% 准确率是不是太夸张"**（一定会被问）：
> "分级那个 100% 是 22 条同源样本，规则表和样本是我一起写的，
> 它验证的是逻辑正确性不是泛化能力。真正有独立意义的是**错误预填率 3.7%**——
> 那是 27 条独立标注样本算的，而且它是约束性指标。
> 真实上线前必须让质量专家独立标注 100 到 200 条复核，我在文档里也这么写了。"

## 三、API 服务（展示工程完整度）

```bash
python -m app.api.service
# 打开 http://127.0.0.1:8000/docs
```

FastAPI 自动生成的交互式文档，16 个端点。可以现场调两个：

```bash
# 创建问题单
curl -X POST http://127.0.0.1:8000/api/issues \
  -H "Content-Type: application/json" \
  -d '{"issue_id":"INS-DEMO-001","raw_text":"前处理间地面有积水，排水口不干净"}'

# 驱动状态机
curl -X POST http://127.0.0.1:8000/api/issues/INS-DEMO-001/advance

# 看审计轨迹（每一步都有记录）
curl http://127.0.0.1:8000/api/issues/INS-DEMO-001/audit

# 看看板
curl http://127.0.0.1:8000/api/stats
```

**话术**：
> "每一步状态转换都写审计日志，只追加不可改——仓储层压根没暴露 update 和 delete 接口。
> 状态机转换带幂等键和版本号，重复提交会返回既有记录并留一条重放审计。"

## 四、另一个项目的 Demo

消防项目有 5 个演示用例：

```bash
cd 消防项目/fire_agents
pip install -r requirements.txt -r requirements-dev.txt
./start_all.sh          # 启动全部服务
./demo.sh 1             # 法规智能问答
./demo.sh 2             # 案件材料分析
# ... 共 5 个用例
```

**可展示的素材**：
- `demo/demo_voice.mp3` —— 真实语音输入样例
- `demo/demo_image.jpg` —— 真实图片输入样例
- `input/立案登记表.docx` + `.pdf` —— 真实格式的文书样例

**话术**：
> "这个项目还有个我觉得挺有价值的设计——文书人工改动检测。
> 人工审批原本只记'通过/驳回'，不记人改了什么。
> 这个 Agent 自动 diff 原稿和改后稿，能发现人工把罚款从五万元改成五十万元这种风险改动，
> 也能发现终稿里出现了知识库里没有的条款。"

## 七、演示前的检查清单

- [ ] `pip install -r requirements.txt` 执行成功（网络不好时可提前装好）
- [ ] `python scripts/demo_end_to_end.py` 跑通，4 个场景无异常
- [ ] `python -m pytest tests -q` → 31 passed
- [ ] `python scripts/run_eval.py` → 输出三套指标
- [ ] 清空演示数据：`rm -f data/fqa.db`（避免上次运行的脏数据）
- [ ] 准备好"100% 准确率怎么解释"的回答（见 §二）

> **演示顺序建议**：先跑 demo（建立直观印象）→ 再跑测试和评测（建立信任）→

> 顺序反了会显得只会讲概念。
