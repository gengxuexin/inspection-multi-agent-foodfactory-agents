# 在项目中的具体角色与产出

> 对应申请表单选项 5（"产品/前端/后端/Agent/部署等"）。
>
> 本文按**交付角色**组织，而不是按项目罗列——因为面试官关心的是
> "你在这个系统里到底负责哪一块、能独立交付什么"。

---

## 一、角色总览

| 项目 | 我的角色 | 覆盖环节 |
|---|---|---|
| **巡检整改多Agent闭环系统** | 全栈 + Agent 架构 + 产品设计 | 需求 → 设计 → 实现 → 测试 → 评测 → 文档 → 部署 |
| **消防智能执法多模态Agent系统** | Agent 架构 + 后端 + 工程化 | RAG 检索 → 多模态编排 → 文书生成 → 安全 → CI → 部署 |
| **食品研发智能决策系统** | 建模 + 验证（本项目为毕业设计延伸） | 数据处理 → 模型 → 优化 → 解释 |

**一句话概括我的角色：**
> **业务侧问题定义 → 技术方案 → Agent 编排 → 确定性规则落地 → 评测验证 → 工程化交付**
> 全链路一个人负责，重点在"让 AI 系统在业务约束下可靠工作"，而非单点算法。

## 二、按交付能力分层

### 2.1 产品 / 需求侧 —— 我做的不是"接需求"，是"定义问题"

| 产出 | 具体内容 | 证据 |
|---|---|---|
| 痛点拆解 | 把"巡检效率低"拆成三个可独立交付的子问题：条款对不上、分级易错、整改假改 | 三个 Agent 的职责边界 |
| 流程重新设计 | 设计"草稿→待映射→待分级确认→待整改→待验证→待复查→已关闭"主链路 + 4 个旁路状态 | 11 状态 23 转换边 |
| **决策权分配设计** | 明确划出"系统可以自动做"和"必须人做"的边界，并写进代码 | 三条硬闸门 |
| 验收标准定义 | 定义 Top-1/Top-3 准确率、A级召回、误杀率等指标及其取舍优先级 | 三套评测 + 阈值网格搜索 |

**最能体现产品思考的一点：**
> 我定义了**"错误预填率优先于预填率"**这个取舍原则。
> 理由是预填错的条款会一路污染分级判断，比不预填更糟。
> 所以阈值调参不是"让指标好看"，而是"在错误预填率可接受的前提下尽量提高预填比例"。
> 这个原则直接写进了评测脚本的选参逻辑。

### 2.2 Agent 架构侧 —— 核心贡献

| 产出 | 具体内容 |
|---|---|
| **Agent 职责划分** | 3 个专业 Agent + 4 个流程 Agent，**Agent 之间不直接对话**，只通过共享状态读写 |
| **状态机设计** | 显式合法转换表 `ALLOWED_TRANSITIONS`，非法转换直接抛 `TransitionError` 不静默通过 |
| **硬闸门设计** | 3 条不可绕过的约束，写在编排器而非 Agent 内 |
| **Agent 输出契约** | 统一 Pydantic Schema，Agent 输出必须过校验才进状态机 |
| **人工任务队列** | 5 类人工任务统一入队，超时自动上推，不依赖人工催办 |
| **降级策略** | LLM 不可用 → 规则分支 + 人工复核，**绝不自动放行** |
| **幂等与重放** | 状态转换带幂等键 + 版本号，支持按 issue_id 重放全链路 |

**消防项目对应产出：**
- 三级级联路由（rag / multimodal / workflow）
- 三态熔断降级（closed / open / half-open）
- LangGraph 状态图编排（`orchestrator_langgraph.py`）
- 文书人工改动检测 Agent（`change-detector`）
- 网关统一鉴权与审计

### 2.3 后端 / 服务侧

| 产出 | 技术点 |
|---|---|
| API 服务层 | FastAPI，16 个端点覆盖全流程 + 待办队列 + 看板 + 状态机描述 |
| 数据模型 | Pydantic v2 统一 Schema，Agent 契约与数据库结构同源 |
| 持久化 | SQLite 仓储（生产可换 PostgreSQL，接口已隔离），只追加审计表 |
| 状态管理 | 问题单共享状态 + 版本号 + 幂等键 |
| 鉴权审计 | 消防项目：网关统一鉴权、常数时间比较防时序攻击、clearance 越界收敛 |
| 日志 | 270 处 print → logging 迁移（消防项目） |

### 2.4 前端 / 交互侧

| 产出 | 技术点 |
|---|---|
| 流式交互 UI | 消防项目：Gradio UI，支持视频/图片/音频多模态输入 |
| 文书待审区 | 草稿先入 `output/pending/`，人工审批通过后才转正式目录 |
| 改动对比报告 | 自动 diff 原稿快照与人工改后稿，输出可归档报告 |
| 交互脚本 | 食品项目：4 场景端到端演示脚本，逐条打印决策依据与闸门判定 |

**说明**：食品项目是后端/Agent 为主的系统，**没有做前端**，
交互层以演示脚本 + API 形式提供。这一点如实标注。

### 2.5 检索 / RAG 侧

| 产出 | 技术点 |
|---|---|
| 条款级知识库 | 按条款编号分块（不按 token 切），保留版本/生效日期/区域/工序/is_ccp/危害类型 |
| 混合检索 | 元数据硬过滤 → 向量+BM25 双路召回 → RRF 融合 → rerank |
| 置信度合成 | rerank 分数 + 双路一致性 + 元数据匹配三路信号 |
| 三档分流 | 预填 / 人工选 Top-3 / 显式弃答 |
| 人工回流 | 选条款结果入库，统计 Top-1 准确率、Top-3 命中、改选率、无匹配率 |
| 评测驱动调优 | 消防项目 5 轮 RAG 迭代，每轮做归因分析（`rag-tuning-journey.md`） |

### 2.6 数据 / 模型侧（食品研发项目）

| 产出 | 技术点 |
|---|---|
| 数据分层建模 | 单因素（局部）与正交（全局）数据分开建模——混在一起 R² 会变负 |
| GPR 配方回归 | 9 样本留一验证 R²=0.642，MAE=1.93；选 GPR 而非随机森林因为提供不确定性估计，可直接喂给贝叶斯优化 |
| 贝叶斯优化 | EI 最大搜索，推荐 5 个新配方，预测评分高于实验最优值 |
| 货架期预测 | Logistic 菌落生长模型，4 个时间点拟合 R²=0.9915，预测 7.4 天达 10⁵ CFU/g |
| 可解释性 | SHAP 分析各因素贡献 |

## 四、需要如实说明的边界

| 项 | 实际情况 |
|---|---|
| **前端** | 食品项目无前端，交互以演示脚本 + API 提供；消防项目用 Gradio |
| **部署** | 有 Dockerfile 和 compose 配置，**未在生产环境实际运行** |
| **真实 LLM/VLM** | 接口已就绪（OpenAI 兼容协议），**默认跑 mock**，真实模型未接入验证 |
| **真实向量库** | 自实现 hashing 投影，非 ChromaDB/FAISS |
| **真实业务数据** | 条款库是内置 15 条示例，非企业真实 HACCP 计划 |
| **上线运行** | 未在真实工厂/客户环境部署过 |
| **团队协作** | **三个项目均为个人独立完成**，无多人协作经验（这是短板，主动说明比被问出来好） |

## 五、面试表述建议

**当被问"你在项目里具体做了什么"时，不要按模块罗列，按这个结构讲：**

> "这个项目里我主要负责四件事。
>
> **第一是问题定义**——把'巡检效率低'拆成三个能独立交付的子问题，
> 并且划清了哪些可以让系统自动做、哪些必须人做。这个划分后来直接变成了代码里的三条硬闸门。
>
> **第二是 Agent 架构**——状态机、路由、硬约束、人工任务队列、降级策略。
> 我的核心判断是：食品安全场景里 Agent 互相说服的代价是整批货放行，
> 所以闸门必须写在编排器里，不能指望 Agent 自觉。
>
> **第三是确定性规则落地**——20 条分级规则和五道证据校验，
> 每条都带条件、判定和理由模板，让质量部能逐条评审而不是信任一个模型输出。
>
> **第四是验证**——105 个单测、三套离线评测、4 场景端到端演示、阈值网格搜索。
> 这块我投入很大，因为食品安全系统里'看起来能跑'和'真的可靠'差距很大。
>
> 我是独立完成的，团队协作这块经验确实不足，这是我接下来想补的。"
