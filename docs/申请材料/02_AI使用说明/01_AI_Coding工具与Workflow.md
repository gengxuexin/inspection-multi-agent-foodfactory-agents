## 二、我的 Agent Workflow

### 核心原则：**AI 负责实现，我负责决策**

我把工作拆成两类任务：

| 任务类型 | 谁主导 | 例子 |
|---|---|---|
| **翻译型**（把明确意图变成代码） | AI 主导 | 写 Pydantic 模型、实现 BM25、写 API 端点、补测试用例 |
| **判断型**（决定该做成什么样） | **我主导** | 决定"打回不重置倒计时"、决定"低置信度必须弃答"、决定阈值取舍原则 |

**判断型任务我不会外包给 AI。** 举个具体例子：设计稿里写"打回后回到待整改"，
看起来只是加个状态跳转，但我在实现时推导出一个反直觉的结论——
**如果打回后倒计时重置，整改人的最优策略就变成"先随便交点什么被打回，倒计时一重置，再拖几天"**，
对 B 级（3个工作日）的问题这能让它无限期悬置。所以我加了一条硬约束：
打回只增加无效整改次数，`deadline` 严格不动。
这个判断不是 AI 生成的，是我在设计时想清楚的，AI 只是把它翻译成代码和 3 个断言测试。

### 实际执行流程

```
① 需求消化          读设计稿 → 提炼成「数据模型 / 硬约束 / 边界情况」三张清单
       ↓
② 架构先定          我先定架构骨架（模块边界、状态机、Agent 契约），再动手
       ↓                ← 这一步不写代码，因为改架构的成本远高于改实现
③ 分模块实现        一次一个模块，AI 主导实现，我审 diff
       ↓
④ 立即验证          每完成一个模块就跑测试，不攒到最后
       ↓                ← 这个习惯救了我好几次：见下方「踩坑记录」
⑤ 端到端跑通        写演示脚本，用真实场景跑完整流程
       ↓
⑥ 评测与调参        建评测集 → 跑指标 → 网格搜索选阈值
       ↓
⑦ 文档与提交        README / 架构文档 / 面试材料 / 提交历史
```

### 与 AI 协作的三条具体做法

**1. 让 AI 先暴露设计缺口，再补实现。**
我第一次让 AI 实现风险分级 Agent 时，它写完 20 条规则就直接交了。我让它加一个"证据不足"的检测，
它补不出来——因为设计稿里根本没定义"温度异常但没给数值"这种情况怎么判。
**这就是设计缺口被暴露出来的时刻。** 我补的规则是：证据不足时默认不低于 B 级（宁可过度升级，不可漏判），
并强制人工确认。这条规则现在在代码里，也有一个专门的测试。

**2. 用"反向测试"锁住容易被破坏的约束。**
正向测试（功能对不对）容易被补，反向测试（系统**不做什么**）最容易在后续迭代中被破坏。
所以我专门写了两类测试：

```python
def test_missing_exif_is_uncertain_not_reject():
    """无 EXIF 判存疑不判打回 —— 防止后续把"证据不足"改成"证据不合格"，
    那会让真整改被误杀，摧毁现场对系统的信任。"""

def test_cannot_close_without_verification():
    """未通过验证+复查，编排器拒绝关闭 —— 防止后续加个"管理员强制关闭"快捷路径。"""
```

**3. 用 AI 做"对抗性审查"，而不是只做"实现"。**
代码写完后，我会让 AI 用"面试官会怎么质疑这个设计"来审一遍。
这个流程抓出来的问题包括：置信度合成公式里 RRF 先验的权重没道理、
`ALLOWED_TRANSITIONS` 漏了 `UNCERTAIN_REVIEW → PENDING_GRADE` 这条人工回路、
human_tasks 表缺 `created_at` 字段导致待办队列查询报错。
**这些都不是我第一遍能想到的。**

## 三、质量门禁（AI 产出必须过的检查）

我的项目里 AI 写的每一行代码都要过这四道：

| 门禁 | 工具 | 检查什么 |
|---|---|---|
| **单测** | pytest | 消防项目 74 个用例，食品项目 31 个用例，全绿 |
| **端到端演示** | `scripts/demo_end_to_end.py` | 4 个真实场景跑通，覆盖全部硬闸门 |
| **离线评测** | `scripts/run_eval.py` | 三套评测 + 阈值网格搜索，输出指标报告 |
| **CI** | GitHub Actions | 推送自动跑测试 + 代码规范（消防项目已接入） |

**关键点：这些是"会失败的门禁"，不是"看起来在跑的检查"。**
比如食品项目里有一条测试专门验证"打回后 deadline 不变"——
如果哪天有人图省事，在打回时重新计算截止时间，这条测试立刻红。

## 四、踩坑记录（AI 协作的真实教训）

这几条都是实际卡住过的，不是编的。

### 坑 1：AI 生成的代码会"看起来对但静默失效"

第一次跑端到端演示，输出全是"已完成"，但我核对发现**所有问题单都停在"待整改"**。
原因是状态机的转换表漏了一条边，异常被 AI 生成的 try/except 吞掉了。
**教训：异常不能被静默吞掉，尤其是状态机里的。** 后来我把"非法转换直接抛错"做成了硬约束 + 专门测试。

### 坑 2：路径层级少算一层

`config.py` 里 `BASE_DIR = Path(__file__).parent.parent` —— 配置文件在 `app/core/` 下，
往上两级是 `app/`，不是项目根。结果数据目录落到了 `app/data/`。
**这个 bug 不会报错，只会让文件存错地方。**
教训：写完路径相关代码要立刻验证实际落盘位置。

### 坑 3：AI 倾向于"把不确定当通过"

第一版证据验证里，元数据缺失（无 EXIF）的情况，AI 实现成了直接打回。
我要求它改成"存疑转人工"，理由是：**无 EXIF 的水印相机本来就没有 EXIF**，
按"证据不合格"处理会误杀真整改。这个改完，误杀率从设计上的必然偏高降到目标可控。

### 坑 4：指标漂亮得不像话

分级评测跑出 100% 一致率，我第一反应是"太好了"，然后意识到：**评测集只有 22 条，
而且规则表和样本是我同源写的**。它验证的是逻辑正确性，不是泛化能力。
我在文档里明确标注了每个数字的适用范围，并且写了"上线前必须由质量专家独立标注 100-200 条复核"。
**教训：好指标要先问"是不是自己给自己出的题"。**

### 坑 5：改了阈值要重跑回归

阈值从 0.75/0.50 调到 0.70/0.45（网格搜索的结果）后，预填率从 37% 提到 52%。
但这改变了分流比例，可能影响状态机流转——所以改完必须重跑 31 个测试和 4 场景演示。
这是**把配置项当代码改**的思维。

## 五、我怎么判断 AI 的产出能不能用

不靠"感觉不错"，靠三个具体动作：

1. **让它解释**。任何一段我看不懂的逻辑，让它逐行讲。讲不清楚的代码不该进仓库。
2. **写反向测试**。我描述"这个功能**不应该**做什么"，让 AI 写测试。如果它写不出来，
   说明我自己的需求描述也是模糊的——这种情况下先澄清需求，不是先写代码。
3. **跑真实数据**。不跑通真实场景的单元测试等于没测。消防项目的 RAG 调优就是靠
   47 条真实标注样本跑出来的，每轮都做归因分析（见 `rag-tuning-journey.md`）。

## 六、统计复现方法

本文所有数字都可以自己验证，不需要相信我：

```python
# 在 ~/.workbuddy/projects/ 下统计各会话的工具调用与 token
import json, glob, datetime
from collections import Counter, defaultdict

byday = defaultdict(lambda: [0, 0, 0])   # 输入, 输出, 工具调用
for f in glob.glob('*/**/*.jsonl', recursive=True):
    if '.file-rollback' in f:
        continue
    for line in open(f, encoding='utf-8', errors='ignore'):
        d = json.loads(line)
        ts = d.get('timestamp')
        if not ts:
            continue
        day = datetime.datetime.fromtimestamp(ts/1000).strftime('%Y-%m-%d')
        m = d.get('message') or {}
        u = m.get('usage') or {}
        byday[day][0] += u.get('input_tokens', 0) or 0
        byday[day][1] += u.get('output_tokens', 0) or 0
        if d.get('type') == 'function_call':
            byday[day][2] += 1

for day in sorted(byday):
    i, o, c = byday[day]
    print(f'{day}  输入 {i/1e6:6.1f}M  输出 {o/1e3:7.1f}K  工具调用 {c}')
```

## 七、一句话总结（面试可直接用）

> 我的 AI 协作方式不是"让 AI 写完我检查"，而是**分层委派**：
> 翻译型的活儿交给 AI 提高速度，判断型的活儿我自己扛。
> 具体做法是架构我先定、AI 分模块实现、每模块立即跑测试、
> 然后专门用一轮"面试官视角"的对抗性审查找漏洞。
> 项目里所有的安全约束——低置信度不硬猜、A级强制人工、打回不重置倒计时——
> 都是我推导出业务后果后要求写进代码的，AI 负责实现和补测试。
