# 项目介绍 —— 巡检整改多Agent闭环系统

> 对应申请表单选项 2（"已完成的AI项目介绍"）。
>
> **项目定位**：面向食品工厂巡检整改场景的多Agent闭环系统原型。
> **我的角色**：全栈 + Agent 架构 + 产品设计（独立完成）。
> **技术栈**：LangGraph · FastAPI · Pydantic v2 · RAG（向量+BM25+RRF+rerank）· VLM · SQLite/PostgreSQL · Redis · Docker · pytest

---

## 一、这是什么

一个把"巡检发现问题 → 对表 → 分级 → 派单 → 整改 → 验证据 → 复查 → 关闭"全流程
系统化的多Agent系统。核心目标不是"让AI替人品控"，
而是**让查表、分级、验证据这三件耗人又容易出错的事被系统接住，决策权保留在人手里**。

**规模**：5,381 行 Python · 3 个专业 Agent · 20 条分级规则 · 五道证据校验
· 11 状态 23 转换边状态机 · 31 个单元测试 · 16 个 API 端点

---

## 二、解决的三个痛点

| 痛点 | 现象 | 我的方案 |
|---|---|---|
| **条款对不上** | 巡检员说"地面积水"，质量员要翻 SSOP 手册查半天 | RAG 检索：元数据硬过滤 → 向量+BM25双路召回 → RRF融合 → rerank → Top-3 候选 |
| **分级易错** | A/B/C 靠人拍脑袋，不同班组长标准不同，A级漏判=整批货放行 | 20 条可执行规则决策表，并行评估取最高等级，**LLM不能单独定A级** |
| **整改假改** | 口头答应、表上写改了其实没改，甚至交上次的照片 | 五道闸门：清单完整性/元数据防旧图/哈希+pHash防复用/VLM语义核验/交叉校验 |

## 三、三个 Agent 怎么工作

### Agent 2：条款映射（RAG 流水线）

**难点**：巡检口语和条款书面语之间有语义鸿沟，"地面积水"直接去搜会引入噪声。

```
巡检口语描述
  → ① 查询要素抽取（现象/对象/区域/工序/偏差类型/危害猜测/关键词），失败字段留空不阻断
  → ② 元数据硬过滤（zone→process→hazard 逐层放宽，记录放宽层级）
  → ③ 双路召回：向量 + BM25，各 k=10
  → ④ RRF 融合（k=60，只看排名不看分数）
  → ⑤ rerank（交叉特征 / 可换 cross-encoder），取 Top-5
  → ⑥ 置信度多信号合成
  → ⑦ 三档分流
```

**置信度合成**（不是单看向量分数）：

| 信号 | 权重 | 作用 |
|---|---|---|
| rerank 归一化分数 | 基准 | 交叉特征重排得分 |
| 双路一致性 | +0.10 | 向量和 BM25 都排 P70 前 → 语义与关键词同时命中 |
| 区域 / 工序 / 危害类型匹配 | 各 +0.05 | 元数据过滤没失效 |
| RRF 先验 | 微调 | 兜底，防分数抖动 |

> **为什么不能只用向量分数**：单分数区分不了"检索偏了导致高分错配"（最危险，会误导分级）
> 和"条款库缺项导致全都不高"（该转人工补库）。前者要拦，后者要放行。

**三档分流**：

| 置信度 | 模式 | 行为 |
|---|---|---|
| ≥ 0.70 | `prefill` | 预填 Top-1，巡检员可改 |
| 0.45–0.70 | `human_select` | 展示 Top-3，**必须人工选，不预填** |
| < 0.45 | `no_reliable_match` | **显式弃答**，提示"未匹配到可靠条款" |

命中 `is_ccp=True` 的条款**不额外加分，但强制人工确认**。

**人工回流**：人工选定结果连同候选列表、原始 Top-1 一起入库，
统计 Top-1 准确率 / Top-3 命中率 / 改选率 / 无匹配率。**只入库做离线评估，不在线训练模型。**

### Agent 3：风险分级（规则决策表）

20 条规则（A01–A08 / B01–B08 / C01–C04），每条带条件、等级、是否需人工确认、理由模板。

**三个关键设计**：

1. **并行评估取最高等级** —— 串行会在第一个命中处短路，结果依赖规则表顺序。
   串行时"过敏原缺失 + 地面积水"会因 A02/B03 顺序不同而给出 A 或 B。
2. **LLM 只在规则全未命中时建议** —— 且建议 A 级强制转人工，模型不得单独定 A。
3. **证据不足默认不低于 B** —— 描述提"温度异常"但没给数值时，标记"待补证"并转人工。

**人工降级留痕**：A级降级必须填理由（代码层强制抛 `ValueError`），
原等级保留在 `original_level` 供复盘，审计日志记改前改后。

### Agent 6：证据验证（五道闸门）

| # | 校验 | 关键拦截 | 成本 |
|---|---|---|---|
| 1 | 清单完整性 | 必交缺项 → 打回（类型由**问题类型+等级**决定，不能自选删除） | 极低 |
| 2 | 元数据 | EXIF 早于派单 → **疑似旧图打回**；无 EXIF → 存疑（不误杀） | 极低 |
| 3 | 历史复用 | sha256 一致 → 打回；pHash ≥0.95 → 打回；0.85–0.95 → **存疑** | 低 |
| 4 | 语义核验 | VLM 三态输出，**仅"明确不符且 conf≥0.8"自动打回** | 高 |
| 5 | 交叉校验 | 与 MES/设备日志矛盾 → 存疑；复检不合格 → 打回 | 中 |

**pHash 分三档的理由**：同一台设备、同一处积水，整改前后拍的背景天然相似。
如果用单阈值 0.95，把中间档直接判"通过"会漏放，判"打回"会误杀真整改——
所以中间档必须**存疑转人工**。

**分流**：

| 分流 | 后续 | 处理人 |
|---|---|---|
| `reject` | 无效整改+1，倒计时继续 | 系统 |
| `human_onsite_review` | 现场确认签字后才进复查 | 质量授权人 |
| `human_review` | 远程复核证据+关联记录 | 质量工程师 |
| `auto_pass` | 进复查抽验 | 系统 |

**A级/CCP 无论自动结果如何都转现场复核**（硬规则，且不计入自动通过率统计）。

## 四、编排：为什么用状态机而不是 Agent 互相聊

**核心判断：食品安全场景里，Agent 互相说服的代价是整批货放行。**

所以架构是 **Orchestrator + 共享状态 + 条件路由 + 硬闸门 + Human-in-the-loop**：

- Agent 之间**不直接对话**，只通过 Pydantic 约束后的共享状态读写
- 状态转换走显式合法转换表 `ALLOWED_TRANSITIONS`，非法转换**直接抛错不静默通过**
- **闸门写在编排器里，不在 Agent 里** —— Agent 自己返回"我判定完了"也没用，编排器该拦还是拦

### 三条硬闸门（写进代码，不是写进文档）

| # | 约束 | 绕过时的行为 |
|---|---|---|
| ① | 低置信度条款映射不得自动定级 | `run_grade()` 抛 `TransitionError` |
| ② | A级/CCP 不得仅凭照片关闭 | 分流强制 `human_onsite_review` |
| ③ | **打回不重置倒计时** | `deadline` 严格不动，`invalid_fix_count` 单独累计 |

**第 ③ 条的推导**（这是我做这个项目最重要的一个判断）：
如果打回后倒计时重置，整改人的最优策略就变成"先随便交点什么被打回，倒计时一重置，再拖几天"。
对 B 级（3 个工作日）能让问题无限期悬置。所以打回只增加无效整改次数，截止时间严格不动。
连续打回 2 次升级一级响应，3 次通知厂长，无效整改次数进部门月度统计。

### 其他工程化设计

| 项 | 实现 |
|---|---|
| 幂等 | 状态转换带幂等键 + 仓储唯一索引占位，重复提交返回既有记录并留 `idempotent_replay` 审计 |
| 审计 | 只追加表，仓储层**不暴露 update/delete** |
| 人工任务队列 | 5 类任务统一入队，超时自动上推 |
| 降级 | LLM 不可用 → 规则分支 + 人工复核，**绝不自动放行** |
| 复查抽验 | A 100% / B 40% / C 15%，**不预先通知现场** |
| CAPA 联动 | 同区域+工序+条款 30 天内复发 → 自动升级并触发 HACCP 计划评审 |

## 五、评测结果

| 评测 | 样本 | 指标 | 结果 | 限定 |
|---|---|---|---|---|
| 条款映射 | 27 条人工标注 | Top-1 / Top-3 | 85.2% / 96.3% | — |
| | | **错误预填率** | **3.7%** | 约束性指标，优先压低 |
| | | 预填率 | 51.9% | 阈值网格搜索确定 |
| 分级 | 22 条 | A级召回 / 精确 | 100% / 100% | ⚠️ **同源样本，仅验证逻辑** |
| | | 人工确认负担 | 50% | A级+CCP+冲突项 |
| 证据验证 | 120 条四类 | 打回精确/召回 | 1.0 / 1.0 | ⚠️ **构造样本** |
| | | **真整改误杀率** | **0%** | ⚠️ 真实场景会更高，目标<5% |

**阈值不是拍脑袋定的**：16 组网格搜索（high ∈ {0.70,0.75,0.80,0.85} × mid ∈ {0.45,0.50,0.55,0.60}），
选参原则是**错误预填率优先压低，再在该前提下尽量提高预填率**。
最终 high=0.70 / mid=0.45（错误预填率不变，预填率 37%→52%）。

**回归保障**：31 个单元测试全绿，重点是**反向测试**——
验证系统"不做什么"（无 EXIF 判存疑不判打回、未验证不许关闭、打回后 deadline 不变）。

## 六、如何跑起来（Demo）

```bash
pip install -r requirements.txt

# 端到端演示：4 个场景，无需任何 API key
python scripts/demo_end_to_end.py

# 离线评测：三套评测 + 阈值网格搜索
python scripts/run_eval.py

# 单元测试
python -m pytest tests -q

# API 服务
python -m app.api.service        # http://127.0.0.1:8000/docs
```

### 演示的四个场景（每个对应一个卖点）

| 场景 | 演示什么 | 看点 |
|---|---|---|
| 1 | B级卫生问题全自动闭环 | 不是什么都让人审 |
| 2 | A级过敏原 | 证据五道校验**全绿**仍强制转现场复核 |

场景 3 和 4 是最有说服力的两个——它们演示的是**约束生效**，不是功能可用。

## 七、生产化差距（如实说明）

| 模块 | 当前实现 | 生产替换 |
|---|---|---|
| 向量检索 | 可复现 hashing 投影（为离线可跑） | ChromaDB / FAISS + 真实 embedding |
| Rerank | 词面重叠 + 元数据交叉特征 | cross-encoder（bge-reranker 等） |
| VLM | mock 启发式（按文件名标注模拟） | 真实视觉模型 + 真实照片库评测 |
| 存储 | SQLite | PostgreSQL + Redis |
| 鉴权 | 无 | JWT/OIDC + 角色（巡检员/质量工程师/质量授权人） |
| 通知 | 仅落库 | 企业微信/钉钉待办与告警 |
| 条款库 | 内置 15 条示例 | 导入企业 HACCP/SSOP/GMP 全文，元数据由质量部校验 |

**替换成本很低**：只需覆盖 `vector_search` / `rerank` / `_chat` / `vlm_verify` 四个函数，
过滤、融合、置信度、闸门、状态机全部不动。

## 八、这个项目让我学到什么

> **最大的收获是约束设计。**
>
> 一开始我也想让 Agent 自己判断，但很快意识到食品安全场景里 Agent 互相说服的代价是整批货放行。
> 硬约束必须写在编排器里，不能指望 Agent 自觉。
>
> 第二个收获是**评测的诚实性**。分级跑出 100% 一致率时我第一反应是"太好了"，
> 然后意识到评测集只有 22 条、规则和样本还是我同源写的——它验证的是逻辑正确性，不是泛化能力。
> 所以我在文档里标注了每个数字的适用范围。
>
> 第三个收获是**误杀比漏放更伤信任**。真整改被打回，现场就会开始想办法绕过系统，
> 那整套防假改就白做了。所以存疑一律转人工，宁可让人多看两眼。
