## 一、这是什么

一个把消防执法场景的**法规问答、多模态案件分析、法律文书生成**串成完整工作流的系统。
不是单点 Demo，而是有**网关鉴权审计、熔断降级、状态图编排、人机协同审批流**的工程化系统。

**规模**：13,271 行 Python · 3 个 Agent 模块 + 1 个网关 + 8 个公共模块（1,435 行）
· 98 个测试函数 · GitHub Actions CI · Docker 部署配置

## 三、架构亮点

### 3.1 网关统一鉴权与审计（440 行）

所有请求经 `gateway.py` 统一入口：

- **内部 Token 常数时间比较** —— 防时序攻击（`hmac.compare_digest` 而非 `==`）
- **clearance 越界收敛** —— 越权访问被限制在授权范围内而非直接崩溃
- **全链路审计** —— 请求、耗时、结果统一落 `common/audit.py`
- **预算控制** —— `common/budget.py` 控制单次请求的资源消耗，防失控

### 3.2 三态熔断降级（`common/resilience.py`）

不是简单的 try/except，而是标准的 `closed / open / half-open` 三态：

```
closed（正常）  → 连续失败超过阈值 → open（熔断，快速失败）
open（熔断）    → 冷却时间到       → half-open（试探）
half-open       → 试探成功 → closed；失败 → open
```

意义：**下游（LLM/OCR/ASR）挂掉时，系统降级而不是整体卡死。**
这在政务/执法场景是硬需求——不能让一个外部服务不可用导致整个执法系统不可用。

### 3.3 三级级联路由（`common/router.py`）

```
query → 意图识别 → ┬─ rag 路径        法规问答（最快）
                   ├─ multimodal 路径  案件材料分析
                   └─ workflow 路径    复杂组合任务（LangGraph 状态图）
```

按任务类型路由到不同处理管线，避免所有请求都走最重的路径。
`orchestrator_langgraph.py`（592 行）用 LangGraph 状态图承载复杂工作流。

### 3.4 文书人工改动检测 Agent（`change-detector`）

**这是我最想讲的一个设计。**

生成草稿 → 人工编辑 → 审批。审批原本只记录"通过/驳回"，**不记录人改了什么**。
这个 Agent 自动对比改动前后，产出可归档的分析报告。

**它解决的四个盲区**：

| 盲区 | 后果 |
|---|---|
| 模板缺陷不闭环 | 人工每次都手改同样的地方，却没人统计过改哪几处，改完也不反哺模板 |
| LLM 抽取错误无法定位 | 分不清是"模型抽错"还是"人理解不同"——两种问题解法完全相反 |
| 风险改动不可见 | 人工把罚款从"五万元"改成"五十万元"，系统无感知 |
| 幻觉无法追溯 | 终稿出现知识库里没有的条款，不能自动报警 |

**实现方式**：生成草稿时在 `output/pending/.origin/` 存原稿快照 →
人工 approve 时自动逐份对比快照与改后稿 → 报告落在 `output/change_reports/` →
写回审批记录的 `change_reports` 字段。

### 3.5 三级字段分流（文书生成）

LLM 抽取的字段分三类，**处理方式不同**：

| 字段类型 | 来源 | 处理 |
|---|---|---|
| **事实** | 案件材料 | 直接填充 |
| **法律** | 知识库检索 | 附条款引用 |
| **待补充** | 两者都没有 | **留空并标记**，绝不编造 |

第三类是关键——**宁可让文书缺字段等人工补，也不能让模型编一个看起来合理的条款编号。**

## 四、RAG 调优：5 轮迭代的完整推理

> 这份文档记录的不是"我调了什么参数"，而是**每一轮怎么发现问题、怎么排除错误假设、怎么验证结论**。
> 面试时它的价值在于：它证明的不是结果，是**方法**。
> 完整文档见项目根目录 `rag-tuning-journey.md`。

### 起点（7 条样本）

```
faithfulness 0.986   answer_relevancy 0.880
context_precision 0.165   context_recall 0.600
```

`context_precision = 0.165` 很低。但**低在哪、为什么低、该改哪里，全都不知道**。
这是 RAG 优化最常见的起点，也是最危险的起点——很容易直接去调权重、换模型、加 reranker，
然后看着分数微动，误以为在优化。

### 第 0 步：先建尺子，再动手术

**问题**：5 条样本算出来的指标，置信区间宽到没有参考价值。用这种数据做决策，等于用体温计量血压。

**做法**：评测集扩到 **47 条**，人工标注，三个维度设计：
- `category`：直查法条 20 / 跨文档综合 21 / 陷阱题 6
- `difficulty`：easy 8 / medium 18 / hard 21
- 原始 7 条**完整保留**，保证与早期结果可比

### 这里踩的第一个陷阱

新评测跑出来总分从 0.95 掉到 0.48。当时第一反应是"**代码退化了**"。

**分层一看**：老 7 条 recall 仍是 1.000，新加的 40 条只有 0.444。
**总分是新样本拉低的，不是代码退化。**

> **方法论**：扩充评测集后，总分变化必须先归因到"样本变化"还是"代码变化"，
> 否则会在错误的方向上浪费一整天。

### 后续迭代的关键动作

| 轮次 | 发现的问题 | 采取的动作 |
|---|---|---|
| 1 | 陷阱题 recall 只有 1/6，4 条都涉及《消防产品目录》 | 加 `is_tier_table` 元数据，检索时降权 0.6 |
| 2 | 降权把用户需要的答案挤出了 top-k | 调整降权策略 |
| 3 | 单条答案 904 字、跨 4 个片段，faithfulness 掉到 0.75 | 改窗口策略 |
| 4 | **34/47 条弃答**，answer_relevancy 长期停在 0.579 | 诊断弃答成因 |
| 5–6 | 弃答是语义判断，不是字符串匹配 | 改用 LLM judge 复用 RAGAS 口径 |
| 6（v7） | — | 重写作答策略：证据不完整也要作答，只在全部片段无关时才弃答 |

### 第 4 轮的诊断（这段最值得讲）

`answer_relevancy` 长期停在 0.579，而 faithfulness 已达 0.99。分层后发现：

| 分组 | 条数 | answer_relevancy 均值 |
|---|---|---|
| **弃答**（"检索内容不足"） | **34** | **0.429** |
| 正常作答 | 13 | **0.969** |

**34/47 条弃答。** RAGAS 的 answer_relevancy 判"答案是否切题"——
一句"检索内容不足"当然不切题。**指标低不是检索差，是不敢答。**

进一步排查发现：**14 条 recall ≥ 0.75 却仍然弃答** —— 属于过度保守，答案就在片段里。

### 第 6 轮的结论（推翻了自己的假设）

我原本假设"少答更安全"。实际改完 v7：

| 指标 | v6 | v7 | 变化 |
|---|---|---|---|
| answer_relevancy | 0.579 | **0.706** | **+0.127** |
| faithfulness | 0.985 | 0.985 | **0.000** |
| context_recall | 0.527 | 0.548 | +0.021 |
| 弃答条数 | 34 | 11 | **−23** |
| 过度保守 | 14 | 2 | −12 |

> **"多作答不换来幻觉"** —— 少弃答 23 条，faithfulness 一条没掉。
> **这推翻了我原本的假设，而推翻假设本身是产出。**

**最终状态**：faithfulness 保持高位（**未牺牲**），answer_relevancy 提升 0.127，
弃答从 34 条降到 11 条。这一点很重要——**RAG 优化最容易的失败是修好一个指标、牺牲另外两个。**

### 一个"我拒绝做"的优化

文档最后记了一次我主动放弃的优化：某个检测器改了 5 版，
v5 之后准确率还在 0.787~0.957 震荡，我就没再写第 6 版规则。

> **产出不是那个函数，而是"我知道什么时候该停止调参"。**

### 一份重要的选型记录（`embedding-selection.md`）

记录了中文 embedding 模型的对比选择过程，包括**向量前缀问题**——
某些 embedding 模型要求特定前缀才能正常工作，不加前缀会导致检索质量断崖下跌。
这类"踩坑"细节往往是区分"跑过"和"用过"的分水岭。

## 八、这个项目让我学到什么

> **第一，指标下降不一定是代码变差。**
> 评测集从 7 条扩到 47 条，总分从 0.95 掉到 0.48。
> 我第一反应是代码退化，分层统计后发现是老样本仍满分、新样本拉低了总分。
> **这次经历让我养成了"先归因、再动手"的习惯。**
>
> **第二，改动检测比改动本身更有价值。**
> 很多系统只关心"有没有人改"，但**"人改了什么、改动是否有风险、模板缺陷能否闭环"**
> 才是让系统持续变好的关键。
>
> **第三，降级能力在生产环境比功能数量重要。**
> 三态熔断、预算控制、常数时间比较这些看着不炫技，
> 但它们决定了系统在外部依赖不稳定时是"慢一点"还是"直接不可用"。
