## 二、为什么用状态机，而不是 Agent 互相调用

设计稿《项目简介（多agent编排）》的核心论点是：

> "食品安全场景里，Agent 互相说服的代价是整批货放行。"

所以本系统的约束是：

1. **Agent 之间不直接对话**，只通过 `IssueStateModel` 共享状态读写；
2. **Agent 输出必须先过 Pydantic 校验**才允许进入状态机（`app/core/schemas.py`）；
3. **状态转换由编排器决定**，`ALLOWED_TRANSITIONS` 显式声明合法转换，非法转换抛错；
4. **闸门在编排器里，不在 Agent 里**——Agent 无权绕过（自己返回"已分级"，编排器仍然拦住）。

对比一下：

| | 自由对话式 | 本系统 |
|---|---|---|
| 谁决定下一步 | Agent 互相说服 | 编排器条件边 |
| 低置信度怎么办 | Agent 可能自己决定 | 编排器强制转人工 |
| A级能否自动关闭 | Agent 可能觉得可以 | 编排器硬拦住 |
| 出问题怎么追责 | 难 | 审计日志逐条可查 |
| 能否重放 | 难 | 按 issue_id 重放 |

`app/graph/langgraph_flow.py` 用 LangGraph 条件边表达了同一套路由；
LangGraph 未安装时自动回退到 `_fallback_run()` 的显式流转，**两条路径行为一致**。

## 三、条款映射：RAG 流水线的每一层在解决什么

### 为什么要"查询要素抽取"在前

巡检口语和条款书面语之间有语义鸿沟。直接拿"地面积水"去搜条款，
会和"积水""积水报警器"等噪声混在一起。所以先把描述拆成
`现象 / 对象 / 区域 / 工序 / 偏差类型 / 危害猜测 / 关键词`，
再让每个下游环节各取所需：区域工序给硬过滤，关键词给 BM25，现象给向量检索。

**抽取失败字段留空，不阻断流程**——巡检员描述不规范是常态，不能因为抽取失败就卡住流程。

### 为什么要元数据硬过滤在全库召回之前

`meta_filter()` 的逻辑：先按 `zone → process → hazard` 逐层过滤，
候选 < 20 条就放宽当前层，并**记录放宽了哪一层**（`relaxed_filter_layers`）。

全库盲目召回的问题是：同一条"温度记录缺失"可能召回 HACCP 计划里的 CCP-01，
也召回 GMP-7.2 的设备校准条款。过滤先砍掉不适用区域/工序的条款，
让 rerank 在更干净的候选集上工作。

### 为什么用 RRF 而不是加权求和

`1/(k + rank)` 只看**排名**不看分数。这样做的直接好处是：
向量检索的分数分布和 BM25 的分数分布量纲完全不同（一个 0~1 余弦，一个可能十几），
加权求和必须先归一化，而归一化方式会显著影响结果。RRF 无需归一化，
是对两路异构分数最鲁棒的融合方式。

### 为什么置信度不能只看 rerank 分数

单看分数无法区分两种失败：

- **检索偏了**：Top-1 分数很高但那个条款不对 → 高置信度错误预填，最危险
- **条款库缺项**：所有条款分数都不高 → 低置信度，转人工补库

所以置信度是多信号合成（`ClauseRetriever.confidence`）：

| 信号 | 权重 | 含义 |
|---|---|---|
| rerank 归一化分数 | 基准 | 交叉特征重排得分 |
| 双路一致性 +0.10 | 加分 | 向量和 BM25 都排 P70 前，语义与关键词同时命中 |
| 区域匹配 +0.05 | 加分 | 元数据硬过滤没失效 |
| 工序匹配 +0.05 | 加分 | 同上 |
| 危害类型匹配 +0.05 | 加分 | 危害类型对齐 |
| RRF 先验 | 微调 | 兜底，防分数抖动 |

注意 **CCP 条款命中不加分，但强制人工确认**——CCP 相关问题误分级的代价
远高于多一次人工确认的成本。

### 为什么错误预填率优先于预填率

预填错条款比不预填**更糟**：预填的条款会一路流到分级 Agent，
错误的 `is_ccp` / `hazard_type` 会污染分级判断，而且巡检员看到已填内容
更容易直接放过。而不预填只是多花几秒人工选择。

所以阈值选择原则是：**在 `wrong_prefill_rate` 可接受的前提下，尽量提高 `prefill` 比例**。
`scripts/run_eval.py` 的网格搜索就是在做这件事。

## 四、风险分级：规则表为什么这样切

### 等级定义（先统一语义，避免规则歧义）

| 等级 | 定义 | 响应要求 |
|---|---|---|
| A | 已发生或极可能发生的食品安全危害，或影响整批/多批次，或 CCP 失控 | 立即围堵，30分钟响应，人工现场复核，24h临时遏制/72h RCA草案 |
| B | 过程失控或系统性偏差，尚未确认产品受影响但有扩散风险 | 2小时响应，局部隔离/加严，3个工作日整改 |
| C | 孤立、局部、可立即纠正，无产品安全直接影响 | 24小时响应，7个工作日整改 |

### 为什么并行评估取最高等级

A/B/C 规则会同时命中一个问题。比如"地面积水，标签过敏原缺失"同时命中
`B03`（一般卫生偏差）和 `A02`（过敏原风险）。**串行评估会在第一个规则处短路**，
取决于规则表顺序，非常脆弱。并行评估 + 取最高等级让结果与规则顺序无关。

同等级多条命中时**全部记录理由**，因为质量部需要知道"为什么是B级"
而不只是"最高那条规则说B级"。

### 边界情况的处理逻辑

| 情况 | 处理 |
|---|---|
| 多条规则命中不同等级 | 取最高；全部命中规则及理由写入问题单 |
| 命中A级但人工降级 | 必须填降级理由和依据条款；`original_level` 保留供复盘 |
| 规则全部未命中 | LLM 建议分支；LLM 建议 A → 强制转人工 |
| 规则命中但证据不足 | 默认不低于 B，标记"待补证"，补证后重新评估 |
| 条款映射为 no_reliable_match | **不自动定级**，人工选条款后再分级 |
| 同一问题既像 B 又像 C | 取 B（宁可过度升级，不可漏判） |

最后两条的代码实现值得注意——`run_grade()` 开头直接检查
`no_reliable_match and not selected_clause_id` 就抛 `TransitionError`，
**不是返回 None，是抛异常**，因为这代表编排层被绕过，是必须暴露的严重问题。

### 规则表维护

每条规则有 `rule_id`、`name`、`reason_template`。质量部可以逐条评审：
- 新增规则来源：LLM 分支中人工定级与建议不一致的样本、A级漏判复盘、法规/HACCP变更
- 每季度评审一次，重点看：A级漏判、频繁被人工降级的规则、**从未命中的规则**

## 五、证据验证：五道闸门的取舍

### 为什么顺序是"先便宜后昂贵"

| 校验 | 成本 | 确定性 | 能拦住什么 |
|---|---|---|---|
| ① 清单完整性 | 极低 | 完全确定 | 缺项（"表上写改了但什么都没交"） |
| ② 元数据 | 极低 | 完全确定 | 旧图/旧记录复用（EXIF 早于派单） |
| ③ 哈希/相似度 | 低 | 完全确定 | 拿上次整改的照片重复交 |
| ④ VLM 语义核验 | 高（模型调用） | 不确定 | 照片拍的是别的地方 |
| ⑤ 交叉校验 | 中 | 较确定 | 证据与 MES/设备日志矛盾 |

前 3 道确定性最强、成本最低，能拦住"表上写改了其实没改"的大多数情况。
建议**先只上线 1–3 道**，用真实历史照片库把相似度阈值调稳，
再开 ④ 的自动打回权限。

### 为什么 pHash 相似度要分三档而不是一个阈值

| 相似度 | 判定 | 理由 |
|---|---|---|
| ≥ 0.95 | 打回 | 几乎确定是同一张图 |
| 0.85 – 0.95 | **存疑** | 可能是同一场景重新拍（比如同一台设备连续两次整改） |
| < 0.85 | 通过 | 真实复用几乎不会低于这个值 |

关键在于**中间档必须存疑而不是放行**。同一台设备、同一处积水，
整改前后拍的照片背景高度相似，相似度天然偏高。如果中间档直接放行，
真实整改会被误杀。

### 为什么 VLM 只对"明确不符"自动打回

`verdict` 有三态而非两态。设计稿写得很清楚：

> "VLM 只对明确不符自动打回，存疑一律转人工，避免误杀真整改。"

原因是 VLM 判定的方差很大——光照、角度、遮挡都会影响结果。
把 VLM 的"不确定"当成"不合格"转成打回，现场就会开始想办法绕过系统。
正确做法是：**VLM 说不行才打回，VLM 说不准就交给人看**。

代码里体现为 `_vlm_to_check()`：`mismatch 且 confidence ≥ 0.8` 才 REJECT，
`match 且 confidence ≥ 0.8` 才 PASS，其他一律 UNCERTAIN。

### 为什么"打回不重置倒计时"是整个系统的核心

四条防假改硬规则里，前三条（证据类型不可自选、证据必须新鲜、历史复用检测）
都是**检测假证据**，第四条是**惩罚拖延**。

如果打回后倒计时重置，整改人的最优策略就是：先随便交点什么被打回，
倒计时一重置，再拖几天。对B级问题（3个工作日）来说，
这个循环可以让问题无限期悬置。

所以打回只增加 `invalid_fix_count`，`deadline` 严格保持不变。
连续打回 2 次升级一级响应，3 次通知厂长。**无效整改次数进部门月度统计**——
这让"表上假改"有了实际成本。

## 七、测试策略

`tests/test_agents.py` 的 31 个用例不是测"函数返回值对不对"，
而是测**设计约束是否被真正强制执行**：

| 测试类别 | 验证的硬约束 |
|---|---|
| 条款版本 | 过期条款不进候选；同 ID 只保留一个生效版本 |
| CCP 强制人工 | 高置信度命中 CCP 仍 `needs_human=True` |
| 低置信度不预填 | mode 必须是 `human_select` 或 `no_reliable_match` |
| 分级取最高等级 | A02 + B03 同时命中 → A 级，且两条理由都在 |
| LLM 不能定 A | LLM 建议 A → 强制人工 |
| 证据不足升级 | 缺监控数值 → `need_human=True`，等级不低于 B |
| A级降级留痕 | 无理由降级抛 `ValueError`；有理由保留 `original_level` |
| 必交缺项打回 | E101 |
| 旧图打回 | E201 |
| 无 EXIF **不**打回 | E203 存疑（防误杀） |
| 哈希复用打回 | E301 |
| A/CCP 强制现场 | 即使全部校验通过也转 `human_onsite_review` |
| 文档字段矛盾打回 | E406 |
| 打回不重置 | `deadline_kept=True`，`invalid_fix_count` 递增 |
| 非法转换抛错 | `_transition` 拒绝非法目标状态 |
| 未验证不许关闭 | 从 `PENDING_FIX` 直接关闭抛 `TransitionError` |
| 无可靠匹配不自动分级 | `run_grade` 抛 `TransitionError` |
| A级不允许延期 | deadline 不变 |
| 审计完整 | seq 连续，操作人/动作齐全 |
| 幂等键 | 重复提交返回同一问题单 |

其中 `test_missing_exif_is_uncertain_not_reject` 和
`test_cannot_close_without_verification` 是**反向测试**——
它们验证系统"不做什么"，这类约束比正向功能更容易在后续迭代中被破坏。
