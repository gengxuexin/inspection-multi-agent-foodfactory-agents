## 偏 RAG 工程深度的简历版本

**巡检整改多Agent闭环系统（RAG 条款映射 + 多模态证据检索）**  
**角色：RAG 流水线设计 / 多Agent核心开发**  
**时间：2025.XX – 2025.XX**

**项目背景**  
面向食品工厂巡检场景，解决“问题描述与 HACCP/SSOP 条款对不上、人工查表慢、低置信度硬猜导致错分级、整改证据真假难辨”的问题。系统由条款映射、风险分级、证据验证三个 Agent 组成；其中条款映射与证据验证以 RAG 检索为核心，风险分级以规则决策表为闸门。设计原则：**LLM 负责查询理解、检索增强与语义核验，规则负责分级与放行闸门，人工保留 A 级确认和现场复核权**。

**核心工作**
- **条款级知识库构建**：按条款编号而非固定 token 切分 HACCP/SSOP/GMP/供应商验收标准，每个 chunk 保留条款 ID、原文、来源文件、版本、生效日期、适用区域/工序、是否 CCP、危害类型等元数据；长条款额外生成摘要块，但召回时原文块优先。导入时对元数据做人工校验，检索时只取 `effective_date <= 当前日期` 的最新版本，过期条款降权并提示。
- **查询理解与硬过滤**：对巡检口语化描述做结构化要素抽取（现象、对象、区域、工序、偏差类型、危害猜测、关键词），抽取失败字段留空不阻断；先按区域/工序/危害类型做元数据硬过滤缩小候选池，候选不足时按 zone→process→hazard 逐层放宽并记录放宽层级，避免全库盲目召回。
- **混合检索与重排**：向量检索 + BM25 双路召回，RRF 融合后接 cross-encoder rerank 取 Top-5；置信度不用单一向量分数，而是由 rerank 归一化分数、双路一致性、元数据匹配多信号合成，并针对 CCP 条款设置强制人工确认标记。
- **阈值分流与弃答**：按高/中/低置信度分“预填 / 人工选 Top-3 / 无可靠匹配”三档，低置信度不硬猜；无可靠召回时显式弃答并提示“未匹配到可靠条款”，人工可选候选或标记新增条款需求，避免错误预填误导后续分级。
- **引用与可追溯**：每条候选输出条款 ID、来源文件、版本、原文片段、匹配理由和检索时间；人工确认后锁定 `selected_clause_id`，保留 `original_top1` 与改选记录，供后续分析“人工改选率”和错配原因。
- **回流与离线评测**：人工选择结果进入映射样本库，统计 Top-1/Top-3 命中率、人工改选率、无可靠匹配率、错误预填率；用 100—200 条历史巡检标注样本网格搜索高/中置信度阈值，原则是**错误预填率优先压低**，再在可接受范围内提高预填比例；few-shot 示例和 rerank 调优基于样本库离线进行，不在线自动改模型。
- **多模态证据检索**：证据验证 Agent 中，对整改照片做文件哈希 + 感知哈希/图像 embedding 相似度比对历史证据库，拦截旧图复用；相似度分“打回/存疑/通过”三档；VLM 输出结构化 `match/mismatch/uncertain` 与理由，仅对明确不符自动打回，存疑转人工，避免误杀真整改。
- **工程化与可观测**：Agent 输出经 Pydantic 结构化约束后进入 LangGraph 状态机；缓存高频 SOP/条款检索结果；记录每次检索的 query 要素、过滤条件、召回/rerank 分数、阈值分流结果和人工改选，接入调用追踪，便于定位是查询抽取、召回、rerank 还是条款库缺项导致错配。

**技术栈**  
LangGraph、LangChain、FastAPI、Pydantic、RAG（ChromaDB/FAISS + BM25 混合检索 + RRF + cross-encoder rerank）、VLM、Function Calling、PostgreSQL、Redis、Docker

### 精简版（简历空间紧张时用）

**巡检整改多Agent闭环系统（RAG 条款映射 + 多模态证据检索）| 核心开发**  
构建条款级 RAG 知识库，按条款编号分块并保留版本、生效日期、适用区域/工序、是否 CCP 等元数据；巡检口语描述经要素抽取后做元数据硬过滤，向量+BM25 双路召回、RRF 融合、cross-encoder rerank；置信度由 rerank 分数、双路一致性和元数据匹配多信号合成，分预填/人工选/无可靠匹配三档，低置信度显式弃答；输出带条款 ID、来源、版本和引用片段，人工选择回流样本库用于阈值调优与离线评测，重点压低错误预填率。证据验证侧用哈希+图像相似度拦截旧图复用，VLM 结构化输出 match/mismatch/uncertain，存疑转人工。技术栈：LangGraph、ChromaDB/FAISS、BM25、RRF、cross-encoder rerank、VLM、FastAPI、Pydantic、Redis。

### 面试 30 秒讲述（RAG 工程视角）

“这个项目里 RAG 不是‘拿一句话搜一下条款库’。我先按条款编号建知识库，保留版本、生效日期、区域工序、是否 CCP 这些元数据；查询侧先抽要素，再做元数据硬过滤，然后向量和 BM25 双路召回、RRF 融合、cross-encoder 重排。置信度不是只看向量分数，而是 rerank 分数、双路一致性和元数据匹配一起合成，分三档：高置信度预填，中置信度必须人工选，低置信度直接弃答，不硬猜。人工选完的结果回流样本库，用来调阈值和做离线评测，重点看错误预填率，因为预填错条款比不预填更糟。证据验证那边也是检索思路，用哈希和图像相似度拦旧图复用，VLM 只对明确不符自动打回，存疑转人工。”

### 写简历时注意替换

1. **不要写没做过的组件**：如果没用 cross-encoder 而用 LLM listwise rerank，就改成“LLM 重排”；没用 ChromaDB 就写实际向量库。
2. **评测指标要能对上**：Top-3 命中率、错误预填率、弃答率、误杀率，至少有一两项是你真实跑过小样本的，面试官会追问样本怎么标、阈值怎么选。
3. **VLM 若只是原型**：写成“设计 VLM 语义核验规则并完成小样本验证”，不要写成已上线自动打回。
4. **回流机制**：强调“离线调阈值和样本库”，不要说“在线自动训练模型”，除非你真的做了。
