下面把证据验证Agent写成**可执行规则表**。设计原则先定清楚：**误杀（把真整改打回）增加现场负担，漏放（假整改通过）让防假改失效；A级/CCP相关问题无论自动结果如何都必须人工现场复核，B/C级自动通过后进入复查抽验。打回不重置倒计时，无效整改次数单独累计。**

---

## 一、验证流水线与判定结果

**五道校验按顺序执行，任一道判定“打回”即终止并返回；判定“存疑”则继续执行后续校验，最终汇总转人工。**

| 判定 | 含义 | 后续动作 |
|---|---|---|
| **通过** | 该道校验无异常 | 进入下一道 |
| **打回** | 明确不合格，无需人工 | 终止验证，无效整改+1，倒计时继续 |
| **存疑** | 自动无法可靠判断 | 继续后续校验，最终汇总转人工复核 |

**证据类型分类**（不同类型校验方式不同）：

| 证据类型 | 示例 | 元数据校验方式 | 语义核验方式 |
|---|---|---|---|
| 照片 | 整改后现场照片 | EXIF拍摄时间/定位 | VLM图像判断 |
| 视频 | 清洁过程录像 | 文件创建时间/时长 | VLM抽帧判断 |
| 文档 | 温度仪导出PDF、记录表扫描件 | 文件属性+内容中的日期 | LLM字段抽取比对 |
| 系统记录 | MES日志、设备运行记录导出 | 系统时间戳+签名 | 规则比对字段值 |

## 二、证据必交清单（按问题类型模板化）

证据类型由**问题类型+等级**决定，整改人不能自选删除必交项。缺项在第一道校验直接打回。

| 问题类型 | 必交证据 | 交叉校验数据源 |
|---|---|---|
| 温度记录缺失/断链 | 温度仪导出文件、校准状态截图、补录说明 | 冷库日志、设备运行记录 |
| 清洁不彻底/积水 | 整改后照片（含时间水印）、清洁消毒记录 | 环境采样结果（如适用） |
| 人员卫生/着装 | 整改后现场照片、班前会记录 | 监控抽查记录 |
| 异物风险（工具/包装破损） | 更换后照片、破损工具报废记录 | 金属探测/X光记录 |
| 标签标识错误 | 更正后标签照片、批次隔离/返工记录 | 放行记录 |
| 虫害设施异常 | 设施修复照片、虫害检查记录 | 服务商报告 |
| 设备参数漂移 | 校准/维修工单、参数恢复截图 | 设备日志、维护记录 |
| 记录缺失/笔误 | 更正后记录扫描件、更正说明 | 原始记录追溯链 |

## 三、决策表：五道校验

### 校验1：清单完整性

| 规则ID | 条件 | 判定 | 理由模板 |
|---|---|---|---|
| E101 | 必交证据类型存在缺项 | **打回** | “缺少必交证据：{missing_types}，整改未完成。” |
| E102 | 提交了非要求类型的证据但必交项齐全 | 通过 | — |
| E103 | 证据文件无法打开/损坏 | **打回** | “证据文件{file}无法读取，请重新提交。” |
| E104 | 证据数量为0 | **打回** | “未提交任何整改证据。” |

### 校验2：元数据校验（防旧图/旧文件）

| 规则ID | 条件 | 判定 | 理由模板 |
|---|---|---|---|
| E201 | 照片EXIF拍摄时间早于派单时间 | **打回** | “照片拍摄时间{exif_time}早于派单时间{dispatch_time}，疑似旧图。” |
| E202 | 照片EXIF拍摄时间晚于提交时间（时间倒挂） | **存疑** | “照片时间{exif_time}晚于提交时间{submit_time}，时间异常，需人工确认。” |
| E203 | 照片无EXIF且无其他时间证明 | **存疑** | “照片缺少拍摄时间元数据，无法确认是否为整改后拍摄。” |
| E204 | 照片定位不在厂区/相关区域范围内 | **存疑** | “照片定位{location}不在预期区域{zone}，需人工确认。” |
| E205 | 文档内日期早于派单时间 | **打回** | “文档{file}内日期{date}早于派单时间，疑似复用旧记录。” |
| E206 | 系统记录时间戳早于派单时间 | **打回** | “系统记录{record}时间{ts}早于派单时间，非本次整改记录。” |
| E207 | 视频文件创建时间早于派单时间 | **打回** | “视频创建时间{ts}早于派单时间，疑似旧视频。” |
| E208 | 元数据齐全且时间在派单后、提交前 | 通过 | — |

### 校验3：历史复用检测（防拿上次照片重复交）

| 规则ID | 条件 | 判定 | 理由模板 |
|---|---|---|---|
| E301 | 文件哈希与历史证据库完全一致 | **打回** | “证据与历史记录{history_id}完全一致，属重复提交。” |
| E302 | 照片感知哈希/图像embedding相似度 ≥ 0.95 | **打回** | “证据与历史记录{history_id}高度相似（相似度{sim}），疑似复用。” |
| E303 | 相似度 0.85—0.95 | **存疑** | “证据与历史记录{history_id}相似度{sim}，需人工确认是否为同一场景新拍。” |
| E304 | 相似度 < 0.85 | 通过 | — |
| E305 | 文档文本相似度 ≥ 0.9 且关键字段值相同 | **打回** | “文档内容与历史记录{history_id}高度一致，疑似复用。” |

### 校验4：语义核验（证据内容是否真的对应整改项）

| 规则ID | 条件 | 判定 | 理由模板 |
|---|---|---|---|
| E401 | VLM判断照片内容与整改项**明显不符** | **打回** | “照片内容与整改要求不符：{vlm_reason}。” |
| E402 | VLM判断**符合**且置信度 ≥ 0.8 | 通过 | — |
| E403 | VLM判断**存疑**或置信度 < 0.8 | **存疑** | “照片内容无法可靠判断是否完成整改：{vlm_reason}。” |
| E404 | 文档字段抽取失败或关键字段缺失 | **存疑** | “文档{file}未能抽取关键字段{fields}，需人工核对。” |
| E405 | 文档关键字段值与整改要求一致 | 通过 | — |
| E406 | 文档关键字段值与整改要求**明确矛盾** | **打回** | “文档字段{field}值为{value}，与整改要求{expected}不符。” |

**VLM输出必须结构化**，不允许自由文本：

```json
{
  "verdict": "match | mismatch | uncertain",
  "confidence": 0.0-1.0,
  "reason": "照片显示地面干燥、排水口无积水，与‘清洁积水’整改要求一致",
  "evidence_refs": ["区域：前处理间地面", "对象：排水口"]
}
```

### 校验5：交叉校验（关联数据是否一致）

| 规则ID | 条件 | 判定 | 理由模板 |
|---|---|---|---|
| E501 | 关联系统记录与证据**明确矛盾** | **存疑** | “证据显示{claim}，但系统记录{record}显示{actual}，数据矛盾。” |
| E502 | 关联系统记录缺失，无法交叉验证 | **存疑** | “缺少{record_type}记录，无法交叉验证整改结果。” |
| E503 | 关联记录与证据一致 | 通过 | — |
| E504 | 复检/采样结果不合格 | **打回** | “复检结果{result}不合格，整改未达效果。” |

## 四、分流规则：自动通过、存疑转人工、A级强制现场

```python
def route_after_validation(issue, checks):
    # 任一道打回 → 直接打回
    if any(c.verdict == "打回" for c in checks):
        return "reject"

    # 汇总存疑
    uncertain = [c for c in checks if c.verdict == "存疑"]

    # A级 / CCP相关：无论自动结果如何，强制人工现场复核
    if issue.level == "A" or issue.clause.is_ccp:
        return "human_onsite_review"

    # B/C级：有存疑 → 人工复核（可远程）；无存疑 → 自动通过进复查抽验
    if uncertain:
        return "human_review"
    return "auto_pass"
```

**分流结果与后续动作：**

| 分流 | 后续动作 | 谁处理 |
|---|---|---|
| **reject** | 无效整改+1，倒计时继续，通知责任人重新提交 | 系统自动 |
| **human_onsite_review** | 质量授权人现场确认，签字后才可进入复查 | 质量授权人 |
| **human_review** | 远程复核证据+关联记录，通过则进入复查抽验 | 质量工程师 |
| **auto_pass** | 进入复查抽验环节 | 系统自动 |

## 五、可执行伪代码

```python
def verify_evidence(issue, submission):
    checks = []

    # 校验1：清单完整性
    c1 = check_completeness(submission, required_types(issue))
    checks.append(c1)
    if c1.verdict == "打回":
        return finalize(issue, checks, "reject")

    # 校验2：元数据
    for ev in submission.evidences:
        checks.append(check_metadata(ev, issue.dispatched_at))

    # 校验3：历史复用
    for ev in submission.evidences:
        checks.append(check_reuse(ev, history_store))

    # 校验4：语义核验
    for ev in submission.evidences:
        if ev.type in ("photo", "video"):
            checks.append(vlm_check(ev, issue.requirement))
        else:
            checks.append(doc_field_check(ev, issue.requirement))

    # 校验5：交叉校验
    checks.append(cross_check(submission, issue.linked_records))

    # 分流
    route = route_after_validation(issue, checks)

    # 打回后果
    if route == "reject":
        issue.invalid_fix_count += 1
        # 倒计时不重置
    return finalize(issue, checks, route)
```

## 六、打回后果与时钟规则

| 规则 | 内容 |
|---|---|
| 打回不重置倒计时 | 整改截止时间不变；打回只增加无效整改次数 |
| 无效整改累计 | 每次打回 `invalid_fix_count += 1`，进入责任部门月度统计 |
| 连续打回升级 | 同一问题连续打回2次→自动升级一级响应；连续3次→通知厂长/质量总监 |
| A级打回 | A级问题任何一次打回，除计数外，强制质量经理知悉 |
| 延期与打回独立 | 延期需质量授权人批准并留痕；打回不能作为延期理由 |
| 关闭门槛 | 必须通过验证+复查（A级需现场复核签字），否则系统不允许关闭 |

## 七、离线评测（上线前必做）

构造四类样本，每类≥30条：

| 样本类型 | 构造方式 | 期望结果 |
|---|---|---|
| 真整改 | 真实合格证据 | 通过（不误杀） |
| 假整改（内容不符） | 照片拍别处/文档字段不符 | 打回或存疑 |
| 旧证据复用 | 历史照片/文档重新提交 | 打回 |
| 证据不全 | 缺必交项/文件损坏 | 打回 |

**评测指标：**

```python
metrics = {
    "reject_precision": ...,   # 打回中真正不合格的比例（防误杀）
    "reject_recall": ...,      # 不合格中被成功打回的比例（防漏放）
    "false_reject_rate": ...,  # 真整改被误打回的比例，目标 < 5%
    "uncertain_rate": ...,     # 存疑比例，过高增加人工负担
    "auto_pass_rate": ...,     # 自动通过比例
}
```

调参原则：
- **false_reject_rate 优先控制**，误杀会摧毁现场对系统的信任。
- 相似度阈值 E302/E303 用真实历史照片库调，不同场景（地面、设备、标签）阈值可能不同。
- VLM 存疑率过高时，先只对明确不符打回，其余转人工，不要强行提高自动判定率。
- A级/CCP 的自动结果只作参考，人工现场复核是硬规则，不参与自动通过率统计。

## 八、边界情况处理

| 情况 | 处理 |
|---|---|
| 照片无EXIF（如水印相机） | 依赖水印时间+定位，仍缺失则存疑转人工 |
| 证据涉及多个整改项 | 按整改项逐项核验，任一不符即打回 |
| VLM服务不可用 | 降级为规则校验+人工复核，不自动通过 |
| 历史证据库无相似记录 | 跳过复用检测，记录“首次证据” |
| 同一问题多次提交 | 每次独立验证，历史复用检测覆盖前次提交 |
| 关联记录系统未接入 | 交叉校验标记“无法验证”，A级转人工，B/C级存疑转人工 |
| 证据为视频 | 抽帧做VLM+哈希，元数据校验文件创建时间 |

这套规则表可直接翻译成代码：每道校验实现 `check_*()` 返回 `{verdict, rule_id, reason}`，`route_after_validation()` 做分流，打回逻辑统一走 `invalid_fix_count` 和倒计时不重置。建议**先上线校验1—3（清单、元数据、复用检测）**，这三道确定性最强、最能直接拦住“表上写改了其实没改”；语义核验和交叉校验作为第二阶段，用评测数据调稳后再开自动打回权限。
